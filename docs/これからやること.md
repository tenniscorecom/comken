# これからやること

comken 本体の残タスク。**ここは「これから」だけを置く場所**で、終わったら消す。
なぜそうしたかの経緯は `docs/仕様書.md` の4章かコミットメッセージへ残す
（ここに履歴を貯めると、何が残っているのか読み取れなくなる）。

## 0. 会社で確かめること（先に answer が要るもの）

答えが出るまで先へ進めない、または進め方が変わるもの。

- [ ] **`comken` コマンドが見つからない件**（報告あり）

      ```bat
      reg query HKCU\Environment /v Path | find /i "comken"   :: 登録されたか
      where comken                                            :: 今のセッションから見えるか
      ```

      登録されているのに `where` で出ないなら、**VS Code をウィンドウごと閉じて開き直す**
      （タブを増やすだけでは環境変数が入れ替わらない）。v0.11.3 で `setx` による通知を
      入れたので、それ以降は反映されやすいはず。

- [ ] **ユーザー PATH の型が壊れていないか**

      ```bat
      reg query HKCU\Environment /v Path
      ```

      `REG_EXPAND_SZ` なら無事。**`REG_SZ` に変わっていて `%USERPROFILE%` が
      絶対パスに展開されていたら、v0.11.2 以前の `setup_comken.bat` が書き換えた跡**。
      動作は続くが、元の表記は失われている。v0.11.3 以降は型を保つので再発しない。

- [ ] **定期取得の「時間帯指定」が何のためだったか**

      **ブラウザ取得の重さ対策だった可能性が高い。** Edge の起動・描画・ダウンロード待ちで
      1本あたり数分かかるので、分散させる必要があった。API（requests）へ移ると
      その制約はほぼ消えるので、**まとめて1回で足りるかもしれない。**

      実測で決められる。1回まとめて流して、`ApiMetrics` の `api-usage=1234/15000`
      （24時間あたりの API コール上限に対する消費）と所要時間を見る。

      分ける必要が残るとすれば、理由は「重さ」ではなく次のどちらか:
      - **API のコール上限**に当たる
      - **業務のタイミング**（朝の作業で使うレポートは6時までに、など）

      後者なら、`download_scheduled()` に**グループを指定できるようにして
      管理表へグループ列を足す**（時刻はスケジューラが持つ、という原則は崩さない）。
      **今は何もしない。** 後から足すのは非破壊的なので、実測してから決める。

- [ ] **BO 環境が何にアクセスできるか**（**ここで除外リストが決まる。最重要**）

      **完全オフラインではなく、ホワイトリスト方式の可能性が高い**（顧客情報を扱うため）。
      Salesforce や Microsoft のドキュメントは見られるという話があり、そうであれば
      **BO でも Salesforce と Downloader が使える**。下の sparse-checkout の除外リストは
      「使えない」前提で書いてあるので、**確認してから確定する**。

      確かめ方:

      | 調べること | やり方 |
      |---|---|
      | Salesforce へ届くか | BO の PC のブラウザで Salesforce を開く。開ければ `requests` でも叩ける（同じ 443）。確実にするなら `python -m comken.toolbox.salesforce check` |
      | Outlook が使えるか | Classic Outlook を起動してメールが受信できるか |
      | ホワイトリストの中身 | 情シスへ確認（推測で決めない） |

      あわせて:
      - `openpyxl` / `selenium` / `pywin32` が入っているか（pip が使えないので、無ければその機能は動かない）
      - **社内 RPA 基盤があるか**（無ければ `rpa.py` も除外でき、書き換えるファイルがゼロになる）
      - 社内 LAN 環境とは**別の PC** か（別なら共有サーバーのパスも別々に持つ）
      - **BO の Python のバージョン**（`python -V`）。下の wheel 持ち込みで要る

- [ ] **BO へ `requests` を入れる**（入れられる見込みとのこと。**入れば一番手数が少ない**）

      入れば、除外も遅延 import も要らずに Salesforce と Downloader がそのまま動く。
      **ネットワークが届くかは別問題**なので、入れたあと `check` で確かめる。

      `requests` は単体では入らない。**依存込みで5つ、合計 600KB ほど**:
      `requests` / `certifi` / `idna` / `urllib3` / `charset_normalizer`

      うち `charset_normalizer` だけが **Python のバージョン専用**
      （`cp314-cp314-win_amd64` のような形）。**BO の Python に合わせて落とす**こと。

      ```bat
      :: インターネットに繋がる PC で（BO のバージョンに合わせる）
      pip download requests -d wheels --only-binary=:all: ^
          --python-version 3.11 --platform win_amd64

      :: wheels フォルダを BO へ持ち込んで
      pip install --no-index --find-links wheels requests
      ```

      **`pip` コマンド自体が使えるかは要確認。** 「pip が使えない」が
      「PyPI に繋がらないだけ」なら上の手順で入る。コマンド自体が禁止なら入らない。

- [ ] **顧客情報を扱う環境で、ローカルへの一時コピーが許されるか**

      `local_copy()`（Access の既定動作・大きなファイルの引き込み）は、**各 PC の
      一時フォルダへファイルをコピーする**。終了時に削除するが、処理中は存在する。
      顧客情報を含むファイルが対象になるなら、BO のルール上それが認められるかを確かめる。
      認められないなら、その処理だけ共有サーバー上で直接開く形に変える必要がある
      （速度と引き換えになる）。

#### 届かなかったとき、または使えないモジュールが増えたときの手段

以下は **2026-08-17 に実機で検証してある**が、**上で足りるなら使わない。**

**リポジトリは分けない。** 代わりに `git sparse-checkout` で、その環境で使えない
モジュールを**チェックアウトへ持ってこない**。ファイルが物理的に無いので、
**VS Code の補完にも出ない**——初学者が「使えるつもりで書いて、実行して初めて気づく」
のを防げる。

**使う判断の目安**: 除外したいものが Outlook 1つなら**使わない**。
Salesforce と Downloader まで使えない（＝業務の中心が動かない）なら使う。

```
GitHub（リポジトリ1つ = コードの正本）
  │
  ├─ 社内LAN 側の共有サーバー   … 全部チェックアウト
  │    comken/ 全部（Salesforce・Outlook 込み）
  │    書き換え: rpa.py / sandbox.py / service.py
  │
  └─ BO 側の共有サーバー        … sparse-checkout で除外
       comken/ から salesforce・outlook・services を除いたもの
       書き換え: rpa.py だけ（RPA 基盤を使うなら）
```

共通部分（core・Excel・CSV・ブラウザ・Access・管理表）は**両方に同じものが入る**。
同じタグを checkout している限り中身は一致する。

**環境ごとに違う値は、ほぼ全部 Salesforce 配下にある**（管理表・履歴のパス、組織の URL）。
BO 側ではそこを除外するので、書き換えが要るのは `rpa.py` の import 文だけになる。
そのため**設定ファイルへ外出しする意味が無い**——出せる値は除外され、残る import 文は
出すと動的 import になって素直さを失う（社内固有の値の置き場所を3回変えて
コード直書きへ戻した 2026-08-15 の判断と、別の道から同じ結論）。

**リリースのたびに両方の共有サーバーで checkout する。** 片方だけ更新するとバージョンが
ずれる（動きはする）。**リポジトリを2つに割った場合と違い、修正は1箇所のまま**なので、
更新を忘れても「片方が古い」で済み、「直し漏れた側が壊れる」にはならない。

リポジトリを2つに割ると共通部分（core・Excel・CSV・ブラウザ・管理表）が複製され、
**修正が2箇所になって直し漏れた側だけが静かに壊れる**。sparse-checkout なら
コードも修正も1箇所のまま、環境ごとの見え方だけを変えられる。

- [ ] BO 環境の共有サーバーで、除外つきのチェックアウトを作る

      **コマンドプロンプトか PowerShell から実行する。Git Bash では壊れる**
      （MSYS のパス変換で `!/comken/...` が `!C:/Program Files/Git/comken/...` に化ける）。

      ```bat
      git clone <URL> \\bo-server\share\tools\comken
      pushd \\bo-server\share\tools\comken
      git sparse-checkout init --no-cone
      git sparse-checkout set --no-cone "/*" "!/comken/toolbox/salesforce" "!/comken/toolbox/outlook" "!/comken/services"
      git checkout v0.11.3
      popd
      ```

      除外するものは**「0.」で BO の実態を確かめてから確定する**。下は仮の案で、
      **BO がホワイトリスト方式で Salesforce へ届くなら、除外は Outlook だけになる**。

      | 候補 | 除外する条件 |
      |---|---|
      | `comken/toolbox/outlook` | Exchange へ届かない（その可能性が高い） |
      | `comken/toolbox/salesforce` | Salesforce へ届かない（**届く可能性あり。要確認**） |
      | `comken/services` | 同上（Downloader が Salesforce を使うため） |
      | `comken/toolbox/rpa` | 社内 RPA 基盤が無い場合 |

      **ブラウザは除外しない**（社内システムを見るのに使う）。
      除外リストが変わっても手順は同じで、`sparse-checkout set` の引数を変えるだけでよい。

      検証済みのこと: 除外しても残りは全て動く／`import comken.toolbox.salesforce` は
      `ModuleNotFoundError` になる／**タグを切り替えても除外は保たれる**。

- [ ] BO 側でも社内固有の3ファイル（除外していないもの）を書き換えて `--skip-worktree`。
      **パスは社内 LAN 側と違う値になる**。チェックアウトが別なので互いに影響しない。

## 4. 判断が要るもの

- [ ] **`salesforce_downloader` が、取りに行かない処理でも `requests` を要求する件**

      `get_scheduled_report()` は**設計上、取りに行かない関数**（管理表を読み、履歴を見て、
      保存済みファイルを返すだけ）。`load_master()` も Excel を読むだけ。`report_id_from_url()`
      は正規表現で URL をパースするだけ。**どれもネットワークを使わない**のに、
      モジュールを import した時点で `requests` が要る。

      ```
      service.py ──→ toolbox.salesforce.sites ──→ toolbox.salesforce ──→ requests
      master.py  ──→ toolbox.salesforce (report_id_from_url) ──→ requests
      ```

      **遅延 import（関数内 import）で回避しようとして、やめた**（2026-08-17）。
      **遅延 import が要るということは、設計のほうが歪んでいる**——`service.py` が
      「取りに行く」と「取得済みを読む」の2つの役割を1ファイルに持っていて、
      `report_id_from_url` は**ネットワークを使わないのにネットワークを使うパッケージに
      置かれている**。import を細工しても、その歪みは消えない。

      直すなら**置き場所のほうを直す**:
      - `report_id_from_url` を `master.py` へ移す（使っているのは `master.py` だけ。
        「管理表の URL 列から ID を抜く」のは**管理表の仕様**であって、
        Salesforce クライアントの仕様ではない）
      - `service.py` の「取得済みを読む」側を別ファイルへ分ける

      **ただし `requests` が入るなら、この問題は実務上は起きない。**
      依存としては過剰なままなので、手を入れるかは配置が落ち着いてから決める。

- [ ] **`tools/set_comken_root.py` を残すか決める。**
      各プロジェクトの3か所（`実行.bat` / `認証情報の登録.bat` / `.vscode/settings.json`）を
      一括で書き換えるツール。**恒久登録（`setup_comken.bat`）を標準手順にしたので、
      前の2つは書き換え不要になった**（`PYTHONPATH` が優先されるため）。
      残るのは `settings.json` だけで、役割が3分の1に縮んでいる。

      **残す理由**: 「動くのに補完だけ効かない」は原因特定が難しい失敗で、それを自動で防げる。
      テストもあるので壊れたら気づける。
      **消す理由**: comken の場所が変わる頻度は低く、そのときだけ手で直せば済む。
      使わないものが増えるほど、場所を変えたときの直し漏れが起きやすくなる
      （`スタブ生成.bat` を廃止したときと同じ論点）。

## 抱えている前提（タスクではないが、忘れると判断を誤るもの）

- **用途はレポートの読み取りが中心。** レコードの追加・更新は Data Loader を使うので、
  `insert` / `update` / `upsert` / `delete` は当面使われない。機能を足すならレポート側へ寄せる
  （仕様書 4.26）
- **JWT フローと公開鍵配布は保留。** `cryptography` が使えないため。準備はしてあるので、
  必要になったら再開する
- **ジェネレータには `@measure` を付けない。** `yield` の間に止まっても「完了」と出てしまい、
  停止位置の特定にならない（仕様書 4.34）
