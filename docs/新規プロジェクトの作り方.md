# 新規プロジェクトの作り方

comken を使う新しいツール（プロジェクト）を作るときの手順。**人が読む手順**と、
**社内の外部 AI チャットに作らせるときの約束**の両方をここに書く。

外部 AI には、`comken_bundle/` の資料を渡したうえで「この資料の通りに新規プロジェクトを作って」と頼む。
そのとき AI は、この文書の「AI が守ること」に従う。

## 1. 作り方は2通り

| 状況 | やり方 |
|---|---|
| comken が入っている PC で作る | `python -m comken init プロジェクト名`。ひな形のコピーと、プロジェクト名・comken の場所の差し込みまで自動で済む。**こちらが基本** |
| 外部 AI チャットに作らせる（AI は comken を動かせない） | この文書の「AI が守ること」に従って、AI がひな形と同じ構成のファイルを出力する |

どちらも、できあがる構成は同じ。**外部 AI の出力は、`init` が作る形の再現**であって、別の構成を考える作業ではない。

## 2. AI が守ること

### 2-1. 出発点は必ずひな形

- 資料の「4_新規プロジェクト向け」に、ひな形（`comken/templates/新規プロジェクト/`）の**全ファイルの中身**が載っている。
  **ここから出発する。** 自分の知っている一般的な Python プロジェクトの構成で書き始めない。
- 次の構成を変えない。ファイルを減らさず、名前を変えず、置き場所を変えない。

```
プロジェクト名/
├─ main.py                  入口。「実行 → エラーの受け止め」だけ。業務処理は書かない
├─ src/
│   ├─ __init__.py
│   └─ run.py               処理の本体（run()）。ここと src/ 配下に業務処理を書く
├─ config.ini.example       非エンジニアが変える値だけ。config.ini は作らない
├─ 実行.bat                  起動用（RPA 基盤の入口でもある）
├─ 認証情報の登録.bat         認証情報を使うときの登録用
├─ pyproject.toml / requirements.txt / .gitignore
├─ .vscode/                 settings.json（comken の場所）・extensions.json
├─ README.md
└─ docs/
    ├─ 使い方.md             実行する人向け
    ├─ 仕様書.md             保守する人向け
    └─ ERRORS.md            エラーが出た人向け（プロジェクト固有の節に追記）
```

### 2-2. 書き換えてよい所・いけない所

| 書き換える | 中身 |
|---|---|
| `src/run.py` と、足した `src/*.py` | 業務処理。ここが主な作業 |
| `config.ini.example` | 項目の追加（セクション名・キー名は大文字。既存のセクション名の並びを使い、新しい名前を作らない） |
| `docs/使い方.md` / `docs/仕様書.md` / `README.md` | `（ここを書く）` と `（プロジェクト名）` を埋める |
| `docs/ERRORS.md` | 「プロジェクト固有のエラー」に追記 |
| `requirements.txt` | 使う外部ライブラリだけ残す |

**書き換えない**: `main.py` の骨格、`実行.bat`、`認証情報の登録.bat`、`.gitignore`、`pyproject.toml`、`.vscode/` の構造。
（`main.py` はプロジェクト名の差し込みだけ。）

差し込みが要る所は2つだけ:

- **プロジェクト名**: `（プロジェクト名）` を実際の名前にする（`main.py`・`docs/仕様書.md`・`docs/使い方.md`・`README.md`）
- **comken の場所**: `実行.bat` の `PYTHON_LIBRARY` と `.vscode/settings.json` の `python.analysis.extraPaths`。
  **AI は本当の場所を知らない**ので、ひな形の値（`\\server\share\tools`）のまま出し、
  「この2か所を実際の場所に直してください」と利用者に伝える。2か所は必ず同じ場所を指す

### 2-3. コードの書き方

- 規約は資料の「1_規約_API索引_実例」に従う（命名・型ヒント・定数・例外・ロギング）。
- 使ってよい comken の名前は、**API 索引に載っているものだけ**。索引にない名前を推測で使わない。
  迷ったら「2_実装全文」で実在を確かめる。`_` 始まりは内部実装なので使わない。
- 設定は `from comken import config` で読む（`config.SECTION.KEY`）。パスや閾値を `run.py` に直書きしない
  （非エンジニアが変える値は `config.ini`、エンジニアしか触らない固定値は Python に書く）。
- 機密情報（パスワード・トークン）は `config.ini` にもコードにも書かない。認証情報の登録の仕組みを使う。

#### ログの量と粒度

AI が書くと、ログが多すぎるか、粒度がそろわないことが多い。**ひな形の `src/run.py` の量が目安**
（処理の最後に `logger.info` が1つ。comken の関数は呼ぶだけで必要なログを自分で出す）。

- `print` は使わない。`logger = logging.getLogger(__name__)` を使い、値は `%s` で渡す（f-string にしない）。
  ログの設定は `main.py` がするので、`logging.basicConfig` を足さない。
- **INFO は処理の節目だけ**: 開始、対象の件数、出力先、完了。運用担当者が後から実行ログを見て経過を追える程度。
- **comken の関数を呼ぶ前後に「〜します」「〜しました」を重ねない**。`CSV` を開く・`Excel` に書く・ブラウザを操作する、は
  comken 側がすでに DEBUG で記録している。自分で足すのは、**分岐の理由**（なぜその経路に入ったか）など、comken のログでは分からないことだけ。
- ループの1行ごとにログを出さない。件数をまとめて1行にする。
- WARNING は「処理は続くが気づいてほしい」とき、ERROR は「処理を中断・スキップした」とき。
  例外をそのまま送出する箇所では、ログを重ねて出さない（`main.py` が受け止めて1回出す）。
- パスワード・トークン・個人情報をログに出さない。

#### コメントの量

**「なぜ」だけを書く。** コードを読めば分かること（「CSV を読み込む」「i に 1 を足す」）は書かない。

- 関数の docstring は、何のための関数かを1〜2行で書く。引数と戻り値を1つずつ説明しない（型ヒントが説明になる）。
- 手順の見出しコメント（`# ステップ1: …`）や、行ごとの言い換えを足さない。
- 書くのは、コードからは読み取れない理由（なぜこの順序か、なぜこの値か、なぜ例外にしないか、業務上の決まり）。
- 一時的なメモには `TODO` / `FIXME` / `NOTE` などの目印を付ける。
- ひな形にある説明コメント（`main.py` の RPA 基盤向けの節、`config.ini.example` の説明）は消さない。
  `run.py` の「ここに処理を書く」の例は、使わないなら消す。

### 2-4. ファイルで渡す

AI がファイルを出力できる環境なら、**チャットに貼らず、ファイルで渡す**。

- フォルダ構成のとおりに、パス付きで出力する（`src/run.py` のように、ひな形と同じ相対パス）。
  複数ファイルは zip にまとめてよい（中身の構成は上の図のまま）。
- 文字コードに注意する。**`.bat` は cp932（Shift_JIS）・改行 CRLF** で保存する（UTF-8 だと日本語が文字化けして動かない）。
  それ以外のテキストは UTF-8。
  AI が cp932 で保存できないときは、`.bat` は出力せず、「`実行.bat` と `認証情報の登録.bat` はひな形のコピーを使ってください」と伝える。
- ファイルを出力できない環境なら、ファイルごとに「パス → コードブロック」の順で貼る。1ファイルずつ、省略しない
  （`...` や「以下同じ」で飛ばさない）。

### 2-5. 作ったあとに必ず確認する

出力する前に、次を**1つずつ確かめて**、確かめた結果を最後に報告する。確認できないものは「未確認」と書く。

1. **ひな形のファイルが全部ある**: 2-1 の図の全ファイルが出力に含まれている。1つでも欠けていたら足す。
2. **ひな形のものを全部使っている**: ひな形に最初から入っている仕組みを、使わずに捨てていないか。
   - `main.py` から `src/run.py` の `run()` を呼んでいる（別の入口を作っていない）
   - 設定は `config.ini.example` 経由で `config` から読んでいる（`argparse` や環境変数で別系統を作っていない）
   - ログは comken のロギングで出している（`print` や独自の `logging.basicConfig` を足していない）
   - 例外は `ComkenError` を受ける形のまま（`except Exception: pass` で握りつぶしていない）
3. **使っていないものが残っていない**: ひな形の例（`run.py` の `SHEET`、コメントアウトの例など）で、
   このプロジェクトが使わないものを消した。`config.ini.example` に、コードが読まない項目がない。
   `requirements.txt` に、コードが import しない外部ライブラリがない。
4. **名前が実在する**: `run.py` などが import している comken の名前が、すべて API 索引にある。
   `config.X.Y` で読んでいる項目が、すべて `config.ini.example` にある（逆も同じ）。
5. **置き換えが済んでいる**: `（プロジェクト名）` と `（ここを書く）` が1つも残っていない。
   README の「このひな形の使い方（エンジニア向け・作り終えたら消す）」の節を消した。
6. **comken の場所は2か所とも同じ**: `実行.bat` と `.vscode/settings.json` が、同じ場所を指している
   （本当の場所が不明なら、ひな形の値のままで、利用者への依頼を書いた）。
7. **ログとコメントの量がひな形並み**: `print` が無い。INFO が節目だけになっている。comken の関数の前後に重ねたログが無い。
   コメントが「なぜ」だけで、コードの言い換えが無い。

## 3. 作ったあとに人がやること

1. `実行.bat` と `.vscode/settings.json` の comken の場所を直す（AI が作った場合）。
2. `実行.bat` を1度動かす → `config.ini.example` から `config.ini` が作られて止まる → 値を書き換えて、もう一度実行する。
3. 認証情報を使うときは `認証情報の登録.bat` で登録する。
4. 動いたら `docs/使い方.md` と `docs/仕様書.md` を実物に合わせる。

## 4. なぜこの形にするか

- ひな形の構成を決めている理由（入口を薄く保つ、設定を `config.ini` に集める、など）は
  [ARCHITECTURE.md](ARCHITECTURE.md) と [HISTORY.md](HISTORY.md)。
- 外部 AI は `python -m comken init` を動かせない。資料に「手順」だけ書くと、AI は一般的なプロジェクト構成で書き始め、
  社内の運用（`実行.bat` が RPA 基盤の入口、`config.ini` の扱い、認証情報の登録）から外れる。
  そのため、ひな形の**中身そのもの**を資料に入れ、作ったあとの確認までを手順にした。
