# コーディング規約（共通）

Excel・CSV・ブラウザ操作などの業務自動化で書くコードの規約の入口。
言語に関係なく守ることをここに書き、言語やライブラリに固有のことは下のファイルに分けている。

| ファイル | 読む人 |
|---|---|
| **この文書**（共通） | コードを書く人全員。最初に読む |
| [CONVENTIONS_PYTHON.md](CONVENTIONS_PYTHON.md) | Python を書く人 |
| [CONVENTIONS_VBA.md](CONVENTIONS_VBA.md) | VBA（Excel マクロ）を書く人 |
| [CONVENTIONS.md](CONVENTIONS.md) | comken を使う人・comken 本体を直す人（comken 固有のルール） |

同じことを複数のファイルに書かない。言語やライブラリを問わないルールはこの文書だけに書き、
各ファイルはこの文書を読んだ前提で書く。

## 1. Python と VBA の使い分け

| 処理 | 使う言語 | 理由 |
|---|---|---|
| 1つのブックの中で完結する処理（色付け・書式・列幅・並べ替えなど） | VBA | ブックを開いたままボタン1つで動かせる。配布もブック1つで済む |
| 複数のファイルにまたがる処理（転記・突合・CSV と Excel の変換など） | Python（comken） | 複数ファイルの読み書き・照合は Python のほうが短く確実に書ける |
| ブラウザ操作・外部システムとの連携 | Python（comken） | VBA では安定して書けない |

迷ったら「そのブックを開いている人が、その場で押したいボタンか」で考える。
そうなら VBA、裏でまとめて流す処理なら Python。

## 2. 誰に向けて書くか

- **コードそのもの**は、初級エンジニアが読める書き方にする
- **エラーメッセージ・画面の文言・使い方の説明**は、非エンジニアが読んで自分で対処できる書き方にする

## 3. 読みやすさを最優先にする

コードは書く時間より読まれる時間のほうがずっと長い。
数か月後の自分や、引き継いだ人が読んで分かることを、速さや短さより優先する。

- 凝った書き方より、素直で長い書き方を選ぶ
- 今必要ない機能は作らない（「いつか使うかも」で足した機能は、たいてい使われずに読む量だけ増やす）
- 直すときは、頼まれた範囲だけを直す（ついでの書き換えは、どこが変わったか分からなくする）
- **同じことをする書き方を2つ作らない**（別名・薄い包み直し・「便利のため」の二つ目の入口を置かない。どちらを使えばよいか迷わせる）

## 4. 名前で役割が分かるようにする

| ルール | 良い例 | 悪い例 |
|---|---|---|
| 役割が分かる名前にする | `load_setting` / `LoadSetting` | `load`, `f`, `Sub1` |
| 略しすぎない | `sheet_name` / `sheetName` | `sn`, `s` |
| はい/いいえ（真偽値）は is / has / can で始める | `is_empty`, `hasHeader` | `empty`, `header` |
| 否定形の名前を使わない | `is_valid` | `is_invalid`（`not is_invalid` が読みにくい） |
| 複数を入れるものは複数形 | `rows` | `row` |

大文字・小文字・アンダースコアの使い方は言語ごとに決めている。各言語の規約を見る。

## 5. 意味の分からない数字・文字列を直接書かない（マジックナンバー禁止）

コードの中に突然出てくる `17` や `"売上データ"` を**マジックナンバー**と呼ぶ。
名前の付いた定数にして、ファイルの先頭にまとめる。

- 読む人が「17 列目が何か」を考えなくて済む
- 列やシート名が変わったとき、直す場所が1か所で済む
- 定数は**全部大文字＋アンダースコア**（`SHEET_NAME`、`COL_AMOUNT`）で書く。
  大文字なら「これは途中で変わらない値だ」と一目で分かる（Python・VBA 共通）

## 6. コメントには「なぜ」を書く

コードを読めば分かる「何をしているか」は書かない。
コードからは読み取れない「なぜこうしているか」を書く。

```text
良い: ネットワーク上の大きなファイルを直接開くと遅く不安定なため、先に手元へコピーしてから開く
悪い: i に 1 を足す
```

一時的なメモには決まった目印を付ける。

| 目印 | 意味 |
|---|---|
| `TODO` | あとで追加・修正する |
| `FIXME` | 分かっている不具合がある |
| `HACK` | きれいでない実装（直す必要がある） |
| `NOTE` | なぜこうなったかの説明 |
| `WARNING` | 触るときに注意が必要 |

チェックツールの警告を止めるコメント（Python の `# noqa`、VBA には無い）を書くときは、必ず理由も書く。

## 7. エラーを隠さない

エラーを無視する書き方（Python の `except: pass`、VBA の `On Error Resume Next` の付けっぱなし）は禁止。
エラーを隠すと、処理が途中で失敗したのに「成功した」ように見え、間違ったデータが後工程へ流れる。

エラーメッセージには **何が・どこで・どうすればよいか** を入れる。

```text
良い: シート「売上データ」が見つかりません（ファイル: 2026年9月.xlsx）。シート名が変わっていないか確認してください
悪い: エラーが発生しました
```

## 8. 開いたものは必ず閉じる

ファイル・ブック・ブラウザ・Excel 本体など、開いたものは処理が途中で失敗しても必ず閉じる。
閉じ忘れると、ファイルがロックされて次の実行や他の人の作業が止まる。
書き方は各言語の規約を見る（Python は `with`、VBA は `Cleanup:`）。

## 9. 頻繁に変わる値はコードの外に出す

毎日・毎月書き換える値（ファイル名・フォルダ・対象月など）や、非エンジニアが変える値は、
コードに書かずに設定の置き場所へ出す。

| 言語 | 置き場所 |
|---|---|
| Python | `config.ini`（書き方は [CONVENTIONS.md](CONVENTIONS.md)） |
| VBA | ブック内の「設定」シート |

コードを開かずに変更できれば、書き換えミスでプログラムを壊すこともない。

## 10. パスワード・個人情報を書かない

パスワード・トークン・ID・メールアドレス・顧客名など、漏れて困るものは
**コードにも設定ファイルにも設定シートにも書かない。**
ファイルは共有フォルダやメールで思った以上に広く出回る。
Python では comken の認証情報の仕組み（DPAPI で暗号化して本人しか読めない場所に保存）を使う。

## 11. 本番のファイルでいきなり試さない

新しく書いた・直したコードは、まずコピーしたファイルで動かして結果を確かめる。
VBA の変更は「元に戻す（Ctrl+Z）」が効かない。Python は comken の dry-run モードで、書き込まずに流れだけ確かめられる。

## 12. 規約を変えたいとき

規約は使いながら育てる。合わない・分かりにくいルールがあれば、
黙って破らずに規約のほうを直す。直すときは「同じことを複数のファイルに書かない」を守る。
