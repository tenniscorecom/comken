comken 本体の残タスク。**ここは「これから」だけを置く場所**で、終わったら消す。
なぜそうしたかの経緯は `docs/仕様書.md` の4章かコミットメッセージへ残す

## 0. 会社で確かめること（先に answer が要るもの）

答えが出るまで先へ進めない、または進め方が変わるもの。

- [ ] **`comken` コマンドが見つからない件**（報告あり）

      ```bat
      reg query HKCU\Environment /v Path | find /i "comken"   :: 登録されたか
      where comken                                            :: 今のセッションから見えるか
      ```

      登録されているのに `where` で出ないなら、**VS Code をウィンドウごと閉じて開き直す**
      （タブを増やすだけでは環境変数が入れ替わらない）。v0.11.3 で `setx` による通知を
      入れたので、それ以降は反映されやすいはず。

- [ ] **ユーザー PATH の型が壊れていないか**

      ```bat
      reg query HKCU\Environment /v Path
      ```

      `REG_EXPAND_SZ` なら無事。**`REG_SZ` に変わっていて `%USERPROFILE%` が
      絶対パスに展開されていたら、v0.11.2 以前の `setup_comken.bat` が書き換えた跡**。
      動作は続くが、元の表記は失われている。v0.11.3 以降は型を保つので再発しない。

- [ ] **定期取得の「時間帯指定」が何のためだったか**

      **ブラウザ取得の重さ対策だった可能性が高い。** Edge の起動・描画・ダウンロード待ちで
      1本あたり数分かかるので、分散させる必要があった。API（requests）へ移ると
      その制約はほぼ消えるので、**まとめて1回で足りるかもしれない。**

      実測で決められる。1回まとめて流して、`ApiMetrics` の `api-usage=1234/15000`
      （24時間あたりの API コール上限に対する消費）と所要時間を見る。

      分ける必要が残るとすれば、理由は「重さ」ではなく次のどちらか:
      - **API のコール上限**に当たる
      - **業務のタイミング**（朝の作業で使うレポートは6時までに、など）

      後者なら、`download_scheduled()` に**グループを指定できるようにして
      管理表へグループ列を足す**（時刻はスケジューラが持つ、という原則は崩さない）。
      **今は何もしない。** 後から足すのは非破壊的なので、実測してから決める。

- [ ] **BO（オフライン）環境の実態**
      - インターネット不可・**社内 LAN には繋がる**、で合っているか（ブラウザで社内システムを見るなら）
      - `openpyxl` / `selenium` / `pywin32` が入っているか（pip が使えないので、無ければその機能は動かない）
      - 社内 LAN 環境とは**別の PC** か（別なら共有サーバーのパスも別々に持つ）

## 1. 共有サーバーへの配置

**いちばん先。** これが終わるまで、他のタスクは机上のまま。

- [ ] 共有サーバーで `git clone` し、リリース済みのタグを checkout する

      ```bat
      pushd \\server\share\tools\comken
      git fetch --tags
      git tag -l                 :: 出ているタグを確認する
      git checkout v0.11.3       :: 上で確認した最新版
      popd
      ```

- [ ] **社内固有の値を書いた3ファイルを実際の値へ書き換え、`--skip-worktree` で守る**

      | ファイル | 何を書き換えるか |
      |---|---|
      | `comken/toolbox/rpa.py` | 社内 RPA 基盤の import 名（`example_libs.v0000` は仮名） |
      | `comken/toolbox/salesforce/sites/sandbox.py` | `DOMAIN_URL` / `CREDENTIAL_PREFIX` / `REPORT_*` |
      | `comken/services/salesforce_downloader/service.py` | 管理表・履歴の置き場所 |

      ```bat
      git update-index --skip-worktree comken/toolbox/rpa.py
      ```

      **書き換えた値をこのリポジトリへ push しない**（公開リポジトリのため）。
      ブラウザのサイトクラスを `comken/toolbox/browser/sites/` へ昇格させたら、
      そのファイルも同じ扱いになる。

- [ ] 各 PC で `setup_comken.bat` を1回実行する
      → `PYTHONPATH` と `PATH` に登録され、`comken init` が打てるようになる。
      **実行後に新しいターミナルを開かないと反映されない。**
      配って実行してもらうときは、bat の先頭の `COMKEN_ROOT_FIXED` に場所を書いておく。

- [ ] 配置後、**互換性ポリシーが効き始める**ことを意識する（仕様書8章）。
      ここから先、公開 API の破壊的変更には旧名の維持と警告が要る。

### BO（オフライン）環境への配置

**リポジトリは分けない。** 代わりに `git sparse-checkout` で、その環境で使えない
モジュールを**チェックアウトへ持ってこない**。ファイルが物理的に無いので、
**VS Code の補完にも出ない**——初学者が「使えるつもりで書いて、実行して初めて気づく」
のを防ぐのが狙い（2026-08-17 に実機で検証済み）。

リポジトリを2つに割ると共通部分（core・Excel・CSV・ブラウザ・管理表）が複製され、
**修正が2箇所になって直し漏れた側だけが静かに壊れる**。sparse-checkout なら
コードも修正も1箇所のまま、環境ごとの見え方だけを変えられる。

- [ ] BO 環境の共有サーバーで、除外つきのチェックアウトを作る

      **コマンドプロンプトか PowerShell から実行する。Git Bash では壊れる**
      （MSYS のパス変換で `!/comken/...` が `!C:/Program Files/Git/comken/...` に化ける）。

      ```bat
      git clone <URL> \\bo-server\share\tools\comken
      pushd \\bo-server\share\tools\comken
      git sparse-checkout init --no-cone
      git sparse-checkout set --no-cone "/*" "!/comken/toolbox/salesforce" "!/comken/toolbox/outlook" "!/comken/services"
      git checkout v0.11.3
      popd
      ```

      除外するものと理由（**BO の実態を確かめてから確定する**。上の「0.」参照）:

      | 除外 | 理由 |
      |---|---|
      | `comken/toolbox/salesforce` | インターネット接続が要る |
      | `comken/toolbox/outlook` | 同上 |
      | `comken/services` | Salesforce Downloader が入っている |

      **ブラウザは除外しない**（社内システムを見るのに使う）。

      検証済みのこと: 除外しても残りは全て動く／`import comken.toolbox.salesforce` は
      `ModuleNotFoundError` になる／**タグを切り替えても除外は保たれる**。

- [ ] BO 側でも社内固有の3ファイル（除外していないもの）を書き換えて `--skip-worktree`。
      **パスは社内 LAN 側と違う値になる**。チェックアウトが別なので互いに影響しない。

## 2. Salesforce の実機確認

**手順**: DPAPI へ登録 → `check` → `report` → `app` → `rotate --stage-only`
秘密の値はコマンドライン引数に渡さず、DPAPI から読ませる。

- [ ] **Refresh Token Flow の疎通確認。** Client Credentials Flow は疎通済み（2026-08-14）だが、
      既定にした Refresh Token 系はまだ実組織で通していない

      ```
      python -m comken.toolbox.salesforce check
      ```

- [ ] **ローテーション API のレスポンス形式を実機で確かめる。**
      いまの実装は公開記事からの推定で、**フィールド名が違う可能性がある**。
      `app` と `rotate --stage-only` が `_consumer_id_of()` / `_staged_credentials_of()` を
      実際に通すので、そこで分かる。違っていたら直すのはその2関数だけ。
      どちらも Salesforce 側の切り替えを起こさない

      ```
      python -m comken.toolbox.salesforce app    --app-id 1CE...
      python -m comken.toolbox.salesforce rotate --app-id 1CE... --stage-only
      ```

- [ ] **レポート管理表（Excel）を実際に作る。** 雛形は次で作れる（記入例2行＋「記入方法」シート入り）。
      編集後は `check` で確かめられる

      ```
      python -m comken.services.salesforce_downloader init レポート管理表.xlsx
      ```

## 4. 判断が要るもの

- [ ] **`tools/set_comken_root.py` を残すか決める。**
      各プロジェクトの3か所（`実行.bat` / `認証情報の登録.bat` / `.vscode/settings.json`）を
      一括で書き換えるツール。**恒久登録（`setup_comken.bat`）を標準手順にしたので、
      前の2つは書き換え不要になった**（`PYTHONPATH` が優先されるため）。
      残るのは `settings.json` だけで、役割が3分の1に縮んでいる。

      **残す理由**: 「動くのに補完だけ効かない」は原因特定が難しい失敗で、それを自動で防げる。
      テストもあるので壊れたら気づける。
      **消す理由**: comken の場所が変わる頻度は低く、そのときだけ手で直せば済む。
      使わないものが増えるほど、場所を変えたときの直し漏れが起きやすくなる
      （`スタブ生成.bat` を廃止したときと同じ論点）。

## 抱えている前提（タスクではないが、忘れると判断を誤るもの）

- **用途はレポートの読み取りが中心。** レコードの追加・更新は Data Loader を使うので、
  `insert` / `update` / `upsert` / `delete` は当面使われない。機能を足すならレポート側へ寄せる
  （仕様書 4.26）
- **JWT フローと公開鍵配布は保留。** `cryptography` が使えないため。準備はしてあるので、
  必要になったら再開する
- **ジェネレータには `@measure` を付けない。** `yield` の間に止まっても「完了」と出てしまい、
  停止位置の特定にならない（仕様書 4.34）
