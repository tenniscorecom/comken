# 配置（共有サーバーへ置く）

comken を**共有サーバーへ置いて、社内の実際の値に合わせるまで**の手順。
配置したあとは、各プロジェクトが共有サーバーの comken を直接参照する。

> **このリポジトリは公開している。** 社内のサーバー名・組織 URL・社内ライブラリ名は
> 仮の値（`\\server\share` / `example--sandbox` / `example_libs`）で書いてある。
> **書き換えた値を push しないこと。**

---

## 1. 共有サーバーへ置く

**置き場所は「PYTHONPATH が通っているフォルダ」そのもの。** その直下に `comken`
パッケージが来る形にする（`<PYTHON_LIBRARY>\comken\__init__.py` があること）。
PYTHONPATH へ入れるのは **comken パッケージの親**で、パッケージ自身ではない。

```
\\server\share\python_library\     ← PYTHONPATH が通っている（= PYTHON_LIBRARY）
  comken\                           ← パッケージ本体
    __init__.py
    runtime.py
  README.md / docs/ / tests/        ← import されないので、並んでいても実害はない
```

**リリース済みのタグだけを checkout する。** ブランチを置くと、そこへコミットした瞬間に
全プロジェクトへ伝播する。

```bat
git clone <URL> \\server\share\python_library
pushd \\server\share\python_library
git fetch --tags
git tag -l                 :: 出ているタグを確認する
git checkout v0.11.3       :: 上で確認した最新版
popd
```

> **`comken\` の中から README へ飛べるようにしておくとよい。**
> パッケージの中（`runtime.py` と同じ階層）に README や docs へのショートカットを
> 置くと、`comken\` を開いた人がそこから説明にたどり着ける。
> **ショートカットは git の管理外**なので、置いても `git status` を汚さない。

## 2. 社内の実際の値へ書き換える

**書き換えるのは2ファイル。** 下の表の行だけを変える。
**docstring やコード例の中にある仮の値は変えない**（変えると、うっかり push したときに
公開リポジトリへ社内の実名が載る）。

### 2-1. `comken/internal/names.py` — 社内ライブラリ群のルートパッケージ名

**値は1か所**（`INTERNAL_LIBRARY_ROOT` 定数）。**docstring やコード例は変えない**。

| 変えるもの | いまの値 | 何にするか |
|---|---|---|
| `INTERNAL_LIBRARY_ROOT` | `INTERNAL_LIBRARY_ROOT = "example_libs.v0000"` | 実名のルートパッケージへ（バージョンを含めて1行で） |

**社内ライブラリは import パスにバージョンが入る**（`社内ライブラリ名.vXXXX.rpa` / `社内ライブラリ名.vXXXX.salesforce`）。
上がるたびに**ここだけ**を直せば、 `RPA_LIBRARY_NAME` / `SALESFORCE_LIBRARY_NAME` を通じて
全プロジェクトが追随する（→ 仕様書 4.19）。

### 2-2. `comken/toolbox/salesforce/sites/sandbox.py` — 組織の情報

| 変えるもの | いまの値 | 何にするか |
|---|---|---|
| `DOMAIN_URL` | `DOMAIN_URL = "https://example--sandbox.sandbox.my.salesforce.com"` | My Domain の URL |
| `CREDENTIAL_PREFIX` | `CREDENTIAL_PREFIX = "sandbox"` | 認証情報のキー名の頭（DPAPI に登録した名前） |
| `REPORT_OPPORTUNITIES` | `REPORT_OPPORTUNITIES = "00O000000000001"` | 実際のレポート ID |
| `OWNER` | `OWNER = "comken"` | ライブラリ側のクラスは `comken` を維持（管理者昇格の印） |

**組織を増やすときは、このフォルダにファイルを足して `SITES` に登録する**
（→ `comken/toolbox/salesforce/sites/__init__.py`）。クラス名も組織名に合わせる。

> **注記（2026-08-30）:** Salesforce レポートの集約取得は
> `comken-salesforce-downloader` （別リポジトリ）へ分離したため、
> `comken/services/salesforce_downloader/_paths.py` の書き換えは不要になった。

### 変えなくてよいもの

次にも仮の値が出てくるが、**docstring やコード例・記入例なので変えない**。

| ファイル | 何のための仮の値か |
|---|---|
| `comken/toolbox/salesforce/client.py` / `report.py` / `sites/__init__.py` | docstring のコード例 |
| `templates/新規プロジェクト/実行.bat` / `認証情報の登録.bat` | **雛形**。`comken init` が実際の場所を埋める |

## 3. 書き換えた値を守る

```bat
git update-index --skip-worktree comken/internal/names.py
git update-index --skip-worktree comken/toolbox/salesforce/sites/sandbox.py
```

手元の書き換えが checkout で消えず、うっかり push することもなくなる。

> **これは「コードが変わらない限り」しか守らない。** comken 側でこのファイルを変えた
> リリースへ切り替えると、checkout が止まる。そのときだけ `--no-skip-worktree` で解除し、
> **新しいコードに社内の値を入れ直してから**、もう一度 `--skip-worktree` を設定する。

---

## 4. 各 PC で使えるようにする

```bat
setup_comken.bat
```

`PYTHONPATH` にこのフォルダが登録され、`python -m comken init プロジェクト名` が打てる
ようになる（CLI 入口を `python -m comken` に集約したので `PATH` は触らない）。
**実行後に新しいターミナルを開くこと**（環境変数は起動時に取り込まれる）。
配って実行してもらうときは、bat の先頭の `PYTHON_LIBRARY` に場所を書いておく
（→ [README「プロジェクトの準備」](../../README.md#プロジェクトの準備)）。

---

## 5. 動くか確かめる

```bat
:: comken を読めるか
python -c "import comken; print(comken.__version__)"

:: Salesforce につながるか（副作用なし）
python -m comken sf check

:: プロジェクトを1つ作ってみる
python -m comken init テスト
```

## 配置したあとに効き始めるもの

**公開 API の互換性ポリシー**（→ 仕様書8章）。共有サーバーへ置いて利用プロジェクトが
参照を始めた時点から、名前の変更には旧名の維持と警告が要る。
**破壊的な整理は配置前に済ませておく。**
