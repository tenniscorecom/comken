# Git 社内プレゼン用ネタ（GitHub なし・Git 本体だけでやれること）

社内向けに「Git は GitHub のことではない」を説明するための**羅列**。
プレゼンで使えそうなものを全部並べてあるので、ここから選んで組み立てる。
体裁は他の docs と揃えていない（ネタ帳として使う前提）。

**構成の意図**: 2章に「入れると何が良くなるか」、3章に「入れると何を負うか（セキュリティ含む）」を
**分けて**置いてある。良いことだけ並べると必ず「セキュリティは？」で止まるので、
**リスクは自分から先に出して、対策とセットで見せる**。反論として受けるより通りやすい。

---

## 1. 最初に切り分ける1枚

| 誤解 | 実際 |
|---|---|
| Git を使う＝ソースを外に出す | `git init` は自分のフォルダに `.git` を作るだけ。**通信は一切しない** |
| サーバーを立てる必要がある | 要らない。1人・1台・オフラインで全機能が成立する |
| アカウント登録が要る | 要らない。名前とメールを `git config` に書くだけ（社内メールでよい） |
| GitHub / GitLab が本体 | あれは**置き場所と Web UI**。履歴・差分・復元は全部ローカルの Git がやっている |
| ネットが無いと使えない | ネットを使うのは `push` / `pull` / `clone` の3つだけ。使わなければ通信ゼロ |
| 管理者・運用担当が要る | 1人運用なら不要。共有するときだけ**共有フォルダ1つ**あればよい |
| 新しいソフトを社内に入れる話 | 入れるのは Git 本体1つ（オフラインインストーラあり）。外部サービスとの接続は発生しない |

**社内での実績**: comken（この共有ライブラリ）は共有サーバーに git のチェックアウトを1つ置き、
タグを切り替えるだけで全プロジェクトへ配布している。GitHub は経由していない
（→ [配置](配置.md) / [仕様書「開発とリリース」](../開発/仕様書.md#開発とリリース)）。

## 2. 入れると何が良くなるか（メリット）

### 2-1. 個人に効く

| メリット | いま起きていること | Git を入れた後 |
|---|---|---|
| **戻せる** | 上書き保存して前の状態が消える／どのコピーが正しいか分からない | 任意の時点へ、ファイル単位でも丸ごとでも戻せる |
| **何を変えたか分かる** | 目視で突き合わせる・WinMerge を都度起動する | `git diff` が変わった行だけ出す |
| **なぜ変えたか残る** | 理由は書いた人の頭の中だけ | コミットメッセージに残り、`git log` で後から読める |
| **命名運用が消える** | `最終版_修正3_これ使う.xlsm` が並ぶ | ファイルは1つ。版は履歴側が持つ |
| **試して捨てられる** | 本番ファイルを直接いじる・怖くて直せない | ブランチで試し、ダメならブランチごと捨てる |
| **壊れた時期を特定できる** | 「先週まで動いてたのに」で原因探しが半日 | `git bisect` で二分探索、数分で犯人のコミットが出る |
| **消したコードを掘り出せる** | 昔の処理は探しようがない | `git log -S"文字列"` で消えた行まで検索できる |
| **割り込みに強い** | 作りかけを退避できず消す | `git stash` で棚上げ、戻したら続きから |

### 2-2. チーム・引き継ぎに効く

| メリット | 効き目 |
|---|---|
| **属人化が減る** | `git blame` で「この1行を誰がいつ何のために書いたか」が出る。前任者に聞けなくても追える |
| **引き継ぎ資料が自動で貯まる** | 履歴そのものが経緯の記録になる。引き継ぎのたびに手で書き起こさなくてよい |
| **同時に触っても壊れない** | 「どっちが最新か分からない」が構造的に起きない。衝突は検出されて、そこだけ直す |
| **レビューできる** | 変更が「差分」として見えるので、他人が確認できる単位になる |
| **共有が落ちても止まらない** | 全員が完全な履歴を持つ（分散型）。共有サーバーが死んでも各自の手元で作業は続く |

### 2-3. 運用・組織に効く

| メリット | 効き目 |
|---|---|
| **本番に入っている版が特定できる** | タグで固定する。「今動いてるのはどれ？」が消える |
| **ロールバック手段が実在する** | 前のタグへ戻すだけ。障害時の切り戻しが手順化できる |
| **配布作業が消える** | 共有サーバーのチェックアウトを切り替えると、次の実行から全プロジェクトが新版になる（comken の実運用） |
| **監査に強くなる** | いつ・誰が・何を・なぜ変えたかが機械的に残る。「変更管理をやっていない」状態から抜けられる |
| **変更の申し送りが自動化できる** | `git diff v0.10.0..v0.11.0 --stat` でリリース間の変更一覧が出る |
| **導入コストがほぼゼロ** | サーバー構築・ライセンス費・保守契約なし（Git 本体は無償・オープンソース）。1人でも始められ、合意形成を待たなくてよい |
| **やめるのも簡単** | `.git` フォルダを消せば元のファイル群に戻る。ロックインしない |

## 3. 入れると何を負うか（デメリット・リスク）

**ここを先に出す。** 特にセキュリティは「対策込みで説明できる」ことが導入可否を分ける。

### 3-1. セキュリティ

| リスク | 何が起きるか | 対策 |
|---|---|---|
| **一度コミットした機密は消えない** | パスワード・接続文字列・顧客データをコミットすると、後でファイルから消しても**履歴には残り続ける**。共有済みなら他人の clone にも残る | `.gitignore` で最初から入れない／認証情報は DPAPI へ（→ [credentials](../credentials.md)）／混入したら**値そのものを変更（ローテーション）する**のが本筋。履歴の書き換え（`git filter-repo`）は補助 |
| **`.git` ごとフォルダを渡すと全履歴が渡る** | 「このフォルダ一式ください」でコピーすると、**過去に消したファイルまで**相手に渡る | 外部・他部署へ渡すときは `git archive -o 配布.zip v1.0`（`.git` を含まない）で出す |
| **リポジトリを持ち出せる＝流出単位が大きい** | USB や `git bundle` 1ファイルで**全ソース＋全履歴**が持ち出せる。従来の「1ファイル持ち出し」より被害が大きい | 持ち出し経路は社内規程に合わせる。bundle を使うなら**持ち出し申請の対象**として扱う |
| **共有フォルダの bare リポジトリは ACL でしか守れない** | 認証機構が無い。**読める人＝共有フォルダを読める人**。誰が読んだかのログも Git 側には残らない | 置き場所のアクセス権を先に設計する。機密度の高いものは共有せずローカル運用に留める |
| **コミット者名は自己申告** | `user.name` / `user.email` は自由に書けるので、**「誰がやったか」の証明にはならない**（改ざん検知ではなく記録） | 責任追跡が要るなら共有側のアクセス権と操作ログで担保する（署名まで入れるのは社内では過剰） |
| **氏名・メールが履歴に残り続ける** | 社外へリポジトリを渡すと、コミット者の氏名とメールアドレスが全部付いてくる | 社外へ出す前提のものは `user.email` を業務用に統一。渡すときは `git archive` |
| **社内固有情報が紛れ込む** | サーバー名・組織 URL・社内ライブラリ名が履歴に載る（comken は公開リポジトリなので**仮名で書く運用**にしている） | 「公開するかもしれないもの」は最初から仮名で書く。配置時に実名へ書き換え、`--skip-worktree` で守る（→ [配置](配置.md)） |
| **Git 本体の脆弱性** | 古いバージョンを使い続けると既知の脆弱性が残る | 更新の担当を決める。オフライン環境なら入れ替え手順を決めておく |

### 3-2. 運用・技術

| リスク | 何が起きるか | 対策 |
|---|---|---|
| **Git はバックアップではない** | 同じ PC の `.git` は、ディスクが飛べば履歴ごと消える | 共有フォルダへ push するか、`.git` を含めてバックアップ対象にする |
| **操作を間違えると消える** | `reset --hard` / `checkout` で未コミットの変更が消える。force push は他人の履歴を消す | 使うコマンドを絞る（`add` / `commit` / `log` / `diff` / `restore`）。`reflog` で救えることも多いが、未コミットは救えない |
| **Excel・Access は差分が見えない** | バイナリなので `git diff` が「変わった」しか言わない。**同時編集の自動マージもできない** | 版管理と復元だけを目的にする。同時編集は運用（担当を分ける）で避ける。VBA はエクスポートすればテキスト差分が出る |
| **巨大ファイルでリポジトリが膨らむ** | 大きなバイナリを何度も更新すると、履歴に全版が積もって clone が重くなる | 生成物・データファイルは `.gitignore`。成果物の保管は別の場所へ |
| **共有をネットワーク越しにすると遅い・不安定** | SMB 越しの bare リポジトリは、大きな履歴だと待たされる。切断で操作が中断することもある | 手元での作業は常にローカルで完結する（速い）。共有とのやり取りは push/pull の時だけ |
| **リポジトリが乱立する** | 誰がどこに何を置いたか分からない野良リポジトリが増える | 置き場所と命名を最初に決める。共有するものは1か所に集約する |
| **文字コード・改行・パス長で事故る** | 日本語ファイル名が化ける、改行差分でファイル全体が差分になる、長いパスで失敗する | 5章の初期設定を配る（`core.quotepath` / `core.autocrlf` / `core.longpaths`） |

### 3-3. 人・組織

| リスク | 何が起きるか | 対策 |
|---|---|---|
| **学習コストがある** | 概念（コミット・ブランチ・リモート）が最初は分かりにくい | 最初は5コマンドだけ。VS Code のボタン操作から入る。ブランチは後回しでよい |
| **中途半端だと効果が出ない** | コミットしない日が続く／「作業終わり」で1回だけコミットすると履歴が使えない | 「意味の単位でコミット」を最初に習慣づける |
| **属人化が別の形で残る** | 一人だけが Git を使い、他の人は共有フォルダのコピー運用のまま | 小さく始めて実例を見せる。全員同時導入は狙わない |
| **ツール導入の承認が要る** | 社内規程上、実行ファイルの持ち込みに申請が必要な場合がある | 事前に確認する。GUI クライアント（有償ライセンスのもの）は入れず、**Git 本体＋VS Code** に留めると話が早い |

## 4. やれることの羅列

### 4-1. 1人でも今日から効くこと（サーバー不要・オフライン可）

| やれること | コマンド | 今の社内の何が置き換わるか |
|---|---|---|
| 変更を記録する | `git commit` | `最終版_修正3_これ使う.xlsm` の命名運用 |
| 何をどう変えたか見る | `git diff` / `git diff --stat` | 目視の突き合わせ・WinMerge を都度起動 |
| いつ誰が何をなぜ変えたか | `git log` / `git log --oneline` | 「なんでこの処理入れたんだっけ」 |
| 1コミットの中身を丸ごと見る | `git show <コミット>` | — |
| この1行を書いた人と理由 | `git blame ファイル` | 前任者に聞けない・聞いても覚えていない |
| 消えたコードを探す | `git log -S"文字列"`（ピッケル）/ `git log -G"正規表現"` | 「昔あった処理どこ行った」 |
| 特定ファイルの歴史だけ追う | `git log -p -- path/to/file` | — |
| 変更を捨てて元に戻す | `git restore ファイル` | 上書き保存してしまった |
| コミットを打ち消す（履歴は残す） | `git revert <コミット>` | バックアップから手で戻す |
| ある時点の状態へ丸ごと戻す | `git checkout <タグ/コミット>` | 「先週のフォルダ」を探す |
| 過去版のファイルを1つだけ取り出す | `git show v0.9.0:comken/core/config.py > old.py` | 旧フォルダを漁る |
| 壊れた場所を二分探索で特定 | `git bisect start` → `git bisect run pytest` | 「先週まで動いてたのに」 |
| 作りかけを一時退避する | `git stash` / `git stash pop` | 急な割り込みで作りかけを消す |
| 消したつもりの作業を救出 | `git reflog` | 事故ったときの最後の砦 |
| 管理しないものを決める | `.gitignore` | ログ・生成物・`config.ini` が混ざる |
| 速い全文検索 | `git grep 文字列` / `git grep -n 文字列 v0.9.0` | エクスプローラーの検索 |
| 特定版だけを zip で配る | `git archive -o 配布.zip v0.11.3` | 手でコピーして固める（`.git` が付いていかない） |
| 今どこが変わっているか | `git status` | — |
| 一部の変更だけコミットする | `git add -p` | 「ついでの修正」が混ざる |
| リリース版に名前を付ける | `git tag v1.0.0` | 「本番に入っているのはどれ？」 |
| 前のリリースとの差分一覧 | `git diff v0.10.0..v0.11.0 --stat` | 変更点の申し送りを手で書く |
| 変更のあった行数・頻度を集計 | `git shortlog -sn` / `git log --stat` | 作業実績の可視化 |
| 空白だけの差分を無視して見る | `git diff -w` | インデント修正で差分が埋まる |
| 大文字小文字だけの改名を扱う | `git mv -f` | Windows で気づけない |

### 4-2. 共有フォルダだけで共同作業する（GitHub 不要）

| やれること | 方法 | ポイント |
|---|---|---|
| 共有フォルダをリモートにする | `git init --bare "\\server\share\git\proj.git"` → `git remote add origin "\\server\share\git\proj.git"` → `git push -u origin master` | 必要なのは**ファイル共有だけ**。サービスもポートも要らない（アクセス制御は共有フォルダの権限＝3-1 参照） |
| そこから各自が clone | `git clone "\\server\share\git\proj.git"` | 全員が完全な履歴を持つ（＝共有が落ちても手元で作業できる） |
| リポジトリを1ファイルにして持ち運ぶ | `git bundle create proj.bundle --all` → 相手側で `git clone proj.bundle proj` | **社内LAN ⇔ BO のように環境が分かれているとき**に効く。USB・メールで運べて履歴ごと渡る（＝持ち出しの扱いに注意） |
| 続きだけ運ぶ（差分バンドル） | `git bundle create incr.bundle v0.10.0..master` | 毎回全部を運ばなくてよい。zip コピーと違い**続きから pull できる** |
| 同じリポジトリを複数フォルダに同時展開 | `git worktree add ../proj-hotfix v0.11.3` | 本番版を調べながら開発版を触れる |
| リリース版を固定して配布 | `git fetch --tags` → `git checkout v0.11.3` | comken の配布方式そのもの（→ [配置](配置.md)） |
| 環境固有の書き換えを更新で潰されないようにする | `git update-index --skip-worktree ファイル` | 配置先で書き換えた社内固有の値を守る |
| 誰かの変更を取り込む | `git pull` / `git fetch` + `git merge` | — |
| 衝突したところだけ手で直す | `git status` → 該当箇所を編集 → `git add` | 「どっちが最新か分からない」が構造的に起きない |
| 相手の作業を見るだけ | `git fetch` + `git log origin/master` | 取り込まずに確認できる |
| メールでパッチを渡す | `git format-patch -1` → `git am 0001-*.patch` | リモートすら無い場合の最終手段 |

### 4-3. 試す・分ける

| やれること | コマンド | 効き目 |
|---|---|---|
| 本番を壊さず試す | `git switch -c 試作` | ダメなら**ブランチごと捨てるだけ** |
| 試したものを本流に入れる | `git merge 試作` | — |
| 特定の修正だけ別の版へ持っていく | `git cherry-pick <コミット>` | 本番だけに緊急修正を当てる |
| 直近のコミットをやり直す | `git commit --amend` | メッセージの打ち間違い |
| コミットをまとめ直す・並べ替える | `git rebase -i` | ※プレゼンでは出さない（7章） |
| ブランチの一覧と現在地 | `git branch -vv` | — |
| 履歴を図で見る | `git log --graph --oneline --all` | 分岐と合流が絵で分かる |

### 4-4. 品質を「気をつける」から「仕組み」へ

| やれること | 方法 | 効き目 |
|---|---|---|
| コミット前に自動チェック | `.git/hooks/pre-commit` に `pytest` / `ruff` | 壊れたものが履歴に入らない |
| 機密の混入を機械で止める | pre-commit でパスワードらしき文字列を検出して弾く | 3-1 の「一度入れたら消えない」への一次防御 |
| 決めた形式以外のコミットを弾く | `commit-msg` フック | 記録の粒度が揃う |
| 改行コードの事故を防ぐ | `.gitattributes` で `* text=auto` | Windows / Linux 混在での差分汚染 |
| Excel・Access も版管理する | 普通に `git add` | 差分は見えないが「**いつの版か・戻せる**」は効く |
| VBA も差分で見る | モジュールを `.bas` へエクスポートして add | テキストになるので `git diff` が効く |
| 生成物を追跡しない | `.gitignore`（`typings/` `logs/` `__pycache__/`） | 「差分が生成物で埋まる」を防ぐ |

## 5. Windows・日本語環境で最初にやる設定

```bat
git config --global user.name  "山田 太郎"
git config --global user.email "yamada@example.co.jp"
git config --global core.quotepath false      :: 日本語ファイル名が \346\... にならない
git config --global core.autocrlf true        :: 改行コードの自動変換（Windows）
git config --global init.defaultBranch master :: 既定ブランチ名を固定
git config --global core.longpaths true       :: 長いパスで失敗しない
```

これだけで日本語のファイル名・フォルダ名の運用が普通に回る。

## 6. 実演の順（15分デモの台本）

1. 空フォルダで `git init` → **`.git` ができただけで、どこにも通信していない**ことを見せる
2. ファイルを作って `git add` → `git commit`
3. わざと壊す → `git diff` で**どこを壊したか**を出す
4. `git restore` で戻す → **バックアップを取っていないのに戻る**
5. もう2〜3回コミット → `git log --oneline` で履歴を見せる
6. `git tag v1.0` → ファイルを変える → `git checkout v1.0` で**丸ごと過去へ**、`git switch -` で戻る
7. `git log -S"関数名"` で**消したはずのコード**を掘り出す（＝3-1 の「履歴からは消えない」の実演も兼ねる）
8. `git blame` で「この行は誰がいつ何のために」
9. 共有フォルダに `git init --bare` → `git push` → 別フォルダへ `git clone`
10. `git bundle create` → **1ファイルになる**ことを見せる（環境をまたぐ話と、持ち出しの注意へ）
11. VS Code のソース管理タブを開き、**ここまで全部ボタンで押せる**ことを見せて終わる

## 7. 想定される質問と答え

セキュリティ系は 3-1 で先に出しているので、ここは**残りの反応**への答え。

| 言われること | 答え |
|---|---|
| 難しそう | 日常で使うのは `add` / `commit` / `log` / `diff` / `restore` の**5つだけ**。しかも VS Code のボタンで押せる |
| ソースが外に出るのでは | 出ない。`git init` はフォルダに `.git` を作るだけ。通信するのは `push` した時だけで、push 先を設定しなければ通信手段そのものが無い |
| 共有フォルダにコピーで足りている | 戻せるのは**コピーを取った瞬間**だけ。取り忘れた日には戻れないし、「何を変えたか」は残らない |
| バックアップと同じでは | 逆に、**Git はバックアップではない**（3-2）。違うのは「理由が残る」「部分的に戻せる」「いつ壊れたかを特定できる」の3つで、バックアップとは併用する |
| 既存の管理台帳／SVN がある | 併用できる。Git は手元だけで完結するので、**導入の合意を取らずに1人で始められる** |
| Excel や VBA には使えない | 版管理と復元は効く。ただし差分は見えず同時編集の自動マージもできない（3-2）。VBA はエクスポートすればテキスト差分が出る |
| 誰が管理するのか | 1人運用なら管理者不在で成立する。共有するときも要るのは**共有フォルダ1つ**でサーバー構築は不要。ただし置き場所の権限設計は要る（3-1） |
| 容量を食うのでは | 圧縮して差分で持つので、フォルダを日付でコピーするより**小さくなることが多い**。例外は巨大バイナリ（3-2） |
| 途中で失敗したら壊れる？ | `git reflog` でほとんどの操作は取り消せる。ただし**コミットしていない変更は救えない** |
| 費用は | Git 本体は無償・オープンソース。ライセンス費も保守契約も無い |
| やめたくなったら | `.git` を消せば元のファイル群に戻る。ファイルの形式は変わらない |

## 8. 話さない方がいいこと（最初の説明では出さない）

`rebase` / `cherry-pick` / `submodule` / `reset --hard` / 分散開発のブランチ戦略。
最初に出すと「難しい」に着地して、2章の価値が伝わらない。
**「1人・オフライン・戻せる」だけで押し切る。**

## 9. 社内の現在地（プレゼンで使える実例）

- 共有サーバーに comken の git チェックアウトを1つ置き、**リリースしたタグだけ**を指している。
  更新は `git fetch --tags` → `git checkout v0.11.3` で、その瞬間に全プロジェクトへ伝播する
- 問題が出たら**前のタグへ戻すだけ**で全プロジェクトが戻る（ロールバック手段が実在する）
- 配置先で書き換える社内固有の値は `git update-index --skip-worktree` で保護している
- 公開リポジトリなので、**社内ライブラリの実名・組織 URL は仮名で書く**運用にしている
  （3-1 の「社内固有情報が紛れ込む」への実際の対処）
- 環境が2つある（社内LAN / BO）ので、`git bundle` は「持ち込み手段」としてそのまま使える

詳細は [配置](配置.md) と [仕様書「開発とリリース」](../開発/仕様書.md#開発とリリース)。
