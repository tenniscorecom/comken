## 1. 設定と非機密情報の扱い

### config.ini は「非エンジニアが自分で変える値」だけ

「触ってよい値」と「触ってはいけない値」が混ざると、渡された人がどれを変えてよいか
判断できなくなる。**config.ini を見せる相手を決めることが、そのまま置き場所の基準になる**。
エンジニアしか触らない固定値は Python コードに書く。

`dry-run` / `debug` を `config.ini` に置かない理由: 実行モードの切り替えは
`with dry_run():` / `with debug():`（**context manager だけ**）で受け取る。
`config.ini` も環境変数も setter も読まない。`with` ブロックだけが唯一の手段。
旧 `[RUN]` セクションは v0.12.0 で廃止済み（`check_run_section` の NG で検出）。

**必須項目を事前チェックしない**理由: `Config.xxx.yyy` を参照した時点で
`ConfigKeyNotFoundError` が止まる。事前チェックを置くと「項目を足しただけで
別のところでエラーになる」事故が起きる（v1.0.0 で `config.require()` を削除済み）。

セクション名・キー名は大文字強制。読み込んだ時点で `ConfigLowerCaseNameError` にし、
小文字混じりエラーを書いた場所から直接指す。

`config.ini` のパスは **config.ini からの相対パス** が既定。区切り文字を含まない値
（`INPUT_FOLDER = input`）は `Path` にならず `str` のままなので、相対パスとして
扱うには `./input` のように `./` を付ける。

*出典: 仕様書.md §4.1*

### ブラウザ設定は config.ini ではなくクラス変数

`DRIVER_PATH` / `WAIT_SECONDS` 等はプロジェクト固有ではなく環境共通のデフォルトなので、
`BrowserOptions` のクラス変数として持ち、プロジェクトはサブクラスで差分だけ上書きする。

サイトごとに1ブラウザを起動し、タブでは分けない。ダウンロード先・起動オプション・
ログイン状態はいずれもブラウザ単位で決まるため、タブで複数サイトを扱うと
「サイトAのCSVがサイトBのフォルダに落ちる」事故が構造的に避けられない。
メモリ 1 ブラウザあたり 200〜400MB 増は、社内数個規模では問題にならない。

入口は `Browsers` に一本化し、サイトが1つでも複数でも書き方を変えない。
`with` を必須にする。`with` なしで起動できると途中で例外が出たときに Edge の
プロセスが残り、次の実行でドライバーの更新まで妨げる。

同期が基本。`start` / `wait` を書いたところだけ非同期にする（重画面の読み込み中に
別サイトを進めたい場合）。`parallel` はこの2つを並べた短縮形。

*出典: 仕様書.md §4.2*

## 2. Excel / ファイル I/O の判断

### Excel（openpyxl）と ExcelCOMHandler の使い分け

openpyxl は数式を書けても計算も検証もしないため comken は数式を自動で入れない。
VBA マクロ・パスワード付き保存が必要なときだけ `ExcelCOMHandler` を使う。

*出典: 仕様書.md §4.3*

### テーブルは定義を壊さず、中のデータを操作する

テーブル名の変更・削除は持たない。openpyxl では構造化参照が追随せず参照していた
数式が `#NAME?` になるため。

*出典: 仕様書.md §4.10*

### 元 DB を更新する場合は、ローカルコピーを書き戻さない

「ローカルにコピーして更新し、終わったら元の場所へ上書きで戻す」方式は採用しない。
更新が必要なときは `local_copy=False` で元 DB を直接開き、Access のエンジンに任せる。

却下理由: 作業中に他人が入力した内容が**データベースごと**失われる／速度の利点が
書き戻しで消える／最後に排他で失敗して手戻りが最大になる／大きなファイルを
ネットワーク越しに書いている最中に切断すると元 DB が壊れる、の4点。

例外は「自分だけが使う DB で、他の誰も触らないと保証できる」場合に限られる。
ただしその場合は、そもそも共有フォルダに置く必要があるかを先に検討する。
更新結果を共有 DB に戻すことが目的なら、**戻さずに済む形**（CSV / Excel 別出力、
結果専用 DB の分離）を先に検討する。

*出典: 仕様書.md §4.15*

### `with` を必須にした（2026-08-25）

`CSV` / `Excel` を読み取り専用でも `with` 必須にした。`with` を外れたインスタンスを
触ると `TableNotOpenError` で停止する。書き方が2通りあると覚える量が増える +
`with` を使わないと一時ファイルが残り続ける実バグがあったため。

*出典: 仕様書.md §4.38.4*

### 拡張子はファイル名に含めて渡す（2026-08-25）

`ext=` / `extension=` 引数を廃止し、拡張子はファイル名の文字列に含めて渡す。
拡張子なしの名前は `FileSuffixMissingError` で止める。

「引数で拡張子を指定」「ファイル名で拡張子を指定」の2通りがあるとどちらが優先されるか
が覚えられず、共有サーバーとローカルの結果が違う事故が起きるため。

*出典: 仕様書.md §4.38.5*

### Excel の表を設定として使う仕組み

行が増えていく設定は config.ini より Excel の表が扱いやすい。
`comken.services.salesforce_downloader.report_master` に読み込み・検証・雛形生成を集約し、
使う側は列を宣言するだけ。

理由:
- **列の定義を1か所に集約**: 「dataclass」と「列名の定数」を別々に持つと
  片方を直しても Excel 編集が反映されない事故になるため
- **辞書で読まない**: `row["名前"]` と書くと打ち間違いが実行時まで分からないため
- **Python の名前は英語、Excel の見出しは日本語**: コード規約を崩さずスペース含む見出しも扱える

*出典: 仕様書.md §4.29*

## 3. Access / Outlook の境界

### Outlook は Classic のみ対応し、送信しない、受信メールの添付とリンクは開かない

Outlook は Classic のみ対応する。New Outlook は COM を持たないため自動操作できず、
Graph API は認証とネットワークが必要でオフライン社内では使えない。

**送信は誤送信が取り返しつかないため実装せず、下書き作成までとする。**

**受信メールの添付ファイルを保存・実行する機能と、本文中のリンクを開く機能は実装しない。**
社内のルールで禁止されている操作をプログラムから開けると、**人が守っているルールを
自動処理が迂回する**ことになり、しかも自動なので誰も気づかない。

そのため `MailMessage` が持つのは `has_attachments`（有無の真偽値）だけで、
添付そのものへは到達できない。業務で添付の中身が要る場合は**送信元へ共有サーバー経由の
受け渡しを依頼する**（メール添付を経路にしない）。

`tests/test_outlook.py` が、添付を保存・展開する名前のメソッドが生えていないことを
検証する。**うっかり足されたときに気づける形**にしておく。禁止を文章だけに置くと、
必要になった誰かが善意で足してしまう。

下書き作成（`save_draft`）で**こちらから添付を付けるのは制限しない**（受信物を開く話と
は別のため）。

*出典: 仕様書.md §4.17*

## 4. 社内ライブラリ呼び出しと run への移管

### comken.toolbox.rpa を削除し comken.run へ移す（2026-09-07）

`comken/toolbox/rpa.py` と対応する例外を削除し、`comken/run.py`（`backoffice` /
`intranet` の最小実装）に置き換えた。

社内 RPA 基盤が再編され外部パッケージへの依存が無くなった（内製化された）ため、
comken 内にラッパーを残しておく意味が無い。中身は空実装（`main()` を呼んで結果を返すだけ）。

`comken.toolbox` は「〜を操作する／〜と通信する」部品の置き場所だが、外部依存が無い
ことで `backoffice` / `intranet` は何とも通信しない単純な関数になった。設定・ログ・
実行モード・例外・定数と同じ層（`comken` 直下）に置くのが妥当。

*出典: 仕様書.md §4.40*

## 5. データ転記・操作モデル

### キーで引く操作は「1件」と「複数件」をメソッドで分ける

`index()` はキーが1件に決まることが前提。重複を黙って後の行で上書きすると、
**転記の結果が静かに変わって気づけない**ため `TableDuplicateKeyError` で止める。
重複が普通のデータは `group_by()` で束ねる。

`allow_duplicates` フラグを持たない理由: 「重複を許す」としか言えず、**どう扱うか
（後勝ちにするのか、全件返すのか）が読めない**うえ、全件返す形にすると戻り値の型が
`dict[str, dict]` から `dict[str, list[dict]]` へ変わる。**引数で戻り値の型が変わる**のは
補完も効かず、規約の「bool 引数よりメソッド名で意味にする」に反する。

*出典: 仕様書.md §4.20*

## 6. Salesforce 関連

### Salesforce は読み取りが主用途で、書き込みは Data Loader に任せる（2026-08-14）

業務側の運用は**レポートからデータを引くこと**が中心で、レコードの追加・更新は
Salesforce 公式の **Data Loader** を使う。comken の `insert` / `update` / `upsert` /
`delete` は実装済みだが、当面は使われない見込み。

機能を足すならレポート取得側（2000行の壁の回避・列名の扱い）に寄せる。
書き込み側は現状維持とし、使う予定が無いまま拡張しない。

*出典: 仕様書.md §4.26*

### 認証方式: External Client App + Authorization Code + Refresh Token Flow

#### 結論

- **External Client App（ECA）** を使う
- 無人バッチの認証は **Authorization Code + Refresh Token Flow**（**既定**）
- **Client Credentials Flow は本番で使わない**。ECA 側でも無効にする
- 実行専用ユーザーを運用し、権限はそのユーザー側で最小限にする
- `client_id` / `client_secret` / `refresh_token` はコードや `config.ini` に書かず、
  Windows DPAPI で保管する
- 401 を受けたときだけ再取得して1回再試行する（期限は予測しない）
- JWT Bearer Flow は将来の移行候補として残す

*出典: salesforce-authentication.md §0 結論*

#### secret が漏えいしたときの違い（最重要）

| 有効な認証フロー | `client_id + client_secret`だけが漏えい | 結果 |
|---|---|---|
| Client Credentials Flow | 2値だけでトークンを要求できる | **危険。実行ユーザーとしてアクセス可能** |
| Web Server / Authorization Code Flow + Refresh Token | `refresh_token` か新しい認可コードが別途必要 | 2値だけでは通常アクセスできない |
| JWT Bearer Flow | `client_secret` を使わず、秘密鍵署名が必要 | 2値だけではアクセスできない |

Refresh Token 方式へ切り替える場合は、**Client Credentials Flow を無効にする**。
同じ ECA で有効にしたままでは漏えいした 2 値だけでアクセストークンを取得できる入口が残る。

運用上の決め手（2026-09-08 補足）: `client_secret` の再発行には社内 IT システム部門への
申請が必要で、Salesforce のローテーション要件（30〜60 日周期）に合わせて毎回申請するのは
手間が大きい。Refresh Token なら「パスワード変更」に近い運用ができ、申請が要らない。

*出典: salesforce-authentication.md §最重要*

#### なぜ External Client App なのか

Salesforce は Spring '26 から新規 Connected App の作成を制限。ECA は開発者側の OAuth
設定と組織管理者のポリシーを分離する。複数組織へ同じライブラリを配る構成と合っている。

*出典: salesforce-authentication.md §1 comken 側の判断*

#### なぜ Refresh Token Flow を既定にするのか

Client Credentials Flow は無人実行に最も素直に合うが、撤回した。決め手は**漏えいした
ときに何が起きるか**。

`client_id` と `client_secret` の 2 値が漏れた場合、Client Credentials Flow では
**その 2 値だけでアクセストークンが取れる**（実行ユーザーとして操作可能）。
Refresh Token Flow のみでは `refresh_token` か新しい認可コードが別途要る。

comken は秘密の値を DPAPI に置くが、**DPAPI は同じ Windows ユーザーなら復号できる**。
運用担当者の PC が侵害されたとき、被害が「値を読まれる」で止まるか
「Salesforce を操作される」まで届くかの差になる。

**引き換えに受け入れたもの**: 初回に**対話的な認可が 1 回だけ必要**。`refresh_token` の
保管と失効監視が増える（いずれも初回と例外時の作業）。Refresh Token Rotation を
有効にすると comken が新しい token を DPAPI へ**自動で書き戻す**ので運用は増えない。

*出典: salesforce-authentication.md §2*

#### なぜ Username-Password Flow ではないのか

Username-Password Flow は Salesforce ユーザーのパスワードを自動処理環境へ置く必要があり、
「パスワードを保管しない」という要件に反するため採用しない。

社内 90 日変更規定との関係: Salesforce は client secret を「定期的に」変更する必要があると
案内している（90 日とは指定していない）。社内規定の client secret への適用は情報セキュリティ
担当へ確認が必要。

*出典: salesforce-authentication.md §3*

#### なぜ JWT Bearer Flow を今すぐ使わないのか

JWT Bearer Flow は共有 client secret の代わりに証明書と秘密鍵を使える。将来 JWT へ
交換できるが現時点では秘密鍵の配布・更新・失効、証明書の期限管理、オフライン環境への
暗号ライブラリ導入について社内運用が確定していない。鍵管理体制が決まった時点で
JWT 移行を再評価する。

*出典: salesforce-authentication.md §4*

### レポート取得の集約と履歴管理

`comken/services/salesforce_downloader` に集約し、何を取るかは管理表（Excel）に、
いつ何を取ったかは履歴（CSV）に集める。

**管理表と履歴は別ファイルにする理由**: 人が Excel で編集するものと、プログラムが
追記するものを同じファイルにすると、開いている間に保存できず履歴が飛ぶ。
履歴を CSV 追記にし、Windows のファイルロックで直列化する。

**原因区分を持たせた理由、例外対応表を持たない理由**: 「設定 / Salesforce /
データなし / ファイル / プログラム」の 5 値で運用する人が履歴だけから「管理表を
直すのか」「Salesforce 管理者へ連絡するのか」を判断できる。例外クラス名との
対応表は持たない（更新漏れが起きるため）。代わりに**例外の型だけ**から機械的に判定する。

**0 件を管理表で宣言させる理由（履歴から自動判定しない理由）**: 「その日たまたま
該当データが無い」が普通のレポートで毎回 `EmptyReportError` が出ると**誤報が
続いて本物の失敗も流される**。履歴の回数から自動判定はしない — 設定ミスで毎日 0 行の
レポートほど早く「正常」に分類される。

**`0件あり` 列だけ既定値 `×` を持たせる理由**: 書き忘れると `×` になり
**厳しい側（エラー）へ倒れる**。誤報が出るだけでデータは失われない。列を足した
瞬間に既存管理表が読めなくなり全プロジェクトの業務が止まる事故を防げる。

*出典: 仕様書.md §4.28*

2026-08-30 に `comken/services/salesforce_downloader` を別リポジトリ

## 7. 祝日・カレンダー判定

### 「会社用カレンダーCSV 1本化」 — 実行時は内閣府 CSV を知らない（2026-09-24）

従来の「内閣府 CSV + 会社休日ルールをそれぞれ読む」構成を大きく整理し直し、
「国民の祝日＋会社休日を合成した 1 ファイル」を Python 実行時と VBA 側の両方が読む形にした。
`tools/build_calendar.py` が内閣府 CSV ＋会社休日ルールから `company_calendar.csv` を
生成し、実行時は標準 `csv` だけで読み込む。旧 `BUNDLED_CSV_PATH` / `EXPORTED_CSV_PATH` /
`export_csv()` / `CalendarSourceError` は削除済み。

理由:

1. **内閣府 CSV の形式変更の影響範囲を生成ツールだけに閉じる**。内閣府 CSV は配布形式が
   微妙に変わることがある。実行時に内閣府 CSV の解析を持たなければ対応コストは
   生成ツール 1 箇所に収まる
2. **Python と VBA が同じ 1 ファイルを読む**。VBA からも同じ CSV をそのまま読めばよい
3. **コード量を大きく減らせる**。`_ComputedSource` は純粋計算で数百行あり年単位の特例も
   保守負担だったが、生成ツールが内閣府 CSV をそのまま焼き込むため不要になった
4. **期限切れ検知の挙動がシンプルになる**。内閣府 CSV は「来年まで」という制約を持つため
   範囲外は `False` 倒し（誤って「祝日扱い」より誤って「平日扱い」の方が安全のため）

*出典: 仕様書.md §4.41*

### カレンダーの元データ・会社休日・生成ツールをパッケージ内へ集約（2026-09-25）

内閣府 CSV・会社休日のルール・生成ツールを、リポジトリ直下の `tools/` から
`comken/core/calendar/`（`data/` と `build.py`）へ移した。

- **理由**: comken の利用者が見られるのは**パッケージ（`comken/comken`）の中だけ**で、リポジトリ直下の
  `tools/` は見えない。会社休日を変えたい人が、ルールも生成ツールも見つけられなかった
- **会社休日のルールは `build.py` 冒頭の Python 定数のまま**（2026-08-25 の「コード直書き」の判断を維持）。
  いったん `company_holidays.csv`（Excel で編集できる形）にしたが、同日のうちに定数へ戻した。
  `build.py` をパッケージ内へ移した時点で、利用者は定数を直接直せる。CSV にすると読み込み・検証・
  テスト・説明が増える一方、会社休日は 6 行で年に数回しか変わらず、直すのは `build` を実行するエンジニア自身なので、割に合わなかった
- 生成ツールは `python -m comken.core.calendar.build` で動く。標準の `csv` だけを使う（core 層は toolbox に依存できないため）
- 実行時の設計（判定は `company_calendar.csv` だけを読む）は変えていない。移行の前後で生成物がバイト単位で同一なことを確認した
- 同梱の `company_calendar.csv` が入力から作り直した結果と一致するかを、テストで毎回確かめる（ルールを直して再生成し忘れるのを防ぐ）

### ダウンローダーの日付計算をカレンダーへ移した（2026-09-25）

Salesforce レポートダウンローダーの `ScheduleRule`（`sheets/schedule.py`）に、カレンダーの仕事が混ざっていた。

- **カレンダーへ移したもの**: 祝日に当たった取得日を前後の営業日へずらす判定の中にあった「次（前）の営業日に着くまで 1 日ずつ進める」ループ。
  `non_business_days_after` / `non_business_days_before`（連休の日付のリストを返す）として `comken.core.calendar` に足した。
  `ScheduleRule` は、そのリストの中に「対象日条件を満たす祝日」があるかを見るだけになった
- **`comken.core.clock.month_end` を使うようにしたもの**: 「月末」の判定を、`(date + 1日).month != date.month` の自前計算から、既にあった `month_end()` との比較に変えた
- **`ScheduleRule` に残したもの**: 管理表の文字列を読む部分（「曜日」「日付」「第N営業日」「月末」）と、取得日の条件（曜日・日付・月末・第N営業日）に合うかの判定。
  これは管理表の仕様そのものなので、カレンダーへは移さない。カレンダーに「日付の条件を表す仕組み」を作ると、抽象化のしすぎになる
- 移した前後で、既存の祝日ずらしのテスト 8 件を 1 つも変えずに通ることを確認した（連休を 1 日分しか返さない壊れた版では、それらが落ちる）

## 8. デバッグモード

### `@measure` は「業務バッチがどの処理で止まったかを後から特定できる」ことが主目的（2026-08-24）

所要時間の記録は副次的な効果。

**開始時にもログを出す**: 終了時にしか出さないと、止まった痕跡は**永久に残らない**。
「1 つ前に完了した処理」の行だけが残り、停止位置が空白になる。`@measure` 付きの入口で
「開始」を出し、終了時は「完了 ○秒」「中断 ○秒」を出す。`BaseException` まで捕捉し
`raise` で必ず再送出する（`KeyboardInterrupt` も拾う）。

**引数・戻り値は出さない**: comken は DPAPI のトークン・client_secret・パスワードを扱うため、
汎用デコレータが自動で引数を出す形だと**いつか秘密の値がログへ載る**危険がある。
「どのメソッドで止まったか」まではライブラリが受け持ち、「どのファイル・どの行で
止まったか」は呼び出し側が処理対象を DEBUG ログへ出す。この分担を `measure` の docstring に明記。

**`with debug():` で切り替える**: dry-run と同じ形。`@measure` のログは
`with comken.debug():` ブロック内でのみ DEBUG ログが出る。dry-run と違ってブロック内でも
業務は正常に流れるので戻し忘れ警告は要らない。環境変数・setter は持たない。

**付ける場所の基準は「外部（ネットワーク・ディスク・別アプリ）を待つか」**。純粋な計算や
内部データ加工には付けない（ログが埋もれる）。ジェネレータ関数には付けない。
`@measure` は呼び出し時と return 時にログを出すが、ジェネレータは呼び出し時にオブジェクトを
返すだけで yield での要素返却は消費者側のため、呼び出し時の「完了」が
**イテレーション開始前**に出てしまい停止位置の特定として機能しない。

**`request()` のような内部経路には付けない**: すべての CRUD が通るため呼び出し元と
二重にログが出る。呼び出し元を 1 段だけに絞り、粒度を「ユーザーが名前を呼ぶメソッド」に
揃える。

*出典: 仕様書.md §4.34*

## 9. ロギング

### ログ設定は入口で明示的に行う

社内環境では `setup_logging(Backoffice)` のように環境クラスを渡して root logger を設定する。
二重出力を見逃さないため、root logger が設定済みなら例外にする。
import 時の自動設定は利用側の設定を壊すため行わない。

**ログ保存先は `LOG_ROOT` と `LOG_FOLDER_NAMES` の二段構成にした。**
`LOG_ROOT` は共有サーバーのログディレクトリを一度書けばよく、端末ごとの差分は
`LOG_FOLDER_NAMES = {"PC-001": "bo-logs", ...}` のフォルダ名だけになる。ログサーバーの
移行（ルートだけ書き換え）と端末ごとの登録変更（フォルダ名だけ）を混ぜずに済ませるのが狙い。
未登録の端末は `LOG_ROOT/_etc/etc_{ホスト名}/` 配下に書かれ業務は止めない。複数あっても
ログが混ざらないようホスト名ごとにサブフォルダを分ける。パス区切りを含む値は `Path` の
`/` 演算子で `LOG_ROOT` が捨てられる罠を避けるため未登録扱い。

**他ライブラリの handler が root に混ざっている場合は `LoggingConflictError` で止める。**
誤って混在したまま進めると既存 handler の出力先やレベルを comken が勝手に変えてしまうため、
別エラーを出して「何がどう混ざっているのか」を運用担当者にそのまま見せられるようにした。
comken の handler 自体の二重呼び出しは引き続き `LoggingAlreadyConfiguredError` で止める。

**混在を許可する場合は `allow_existing=True` を明示する**。「**意図的に**共存させる」
ことを示すためキーワード引数で書かせる。comken の handler が両方走った後にもう一度
`setup_logging()` / `setup_local_logging()` を呼ぶケースは許可しない — 何が 3 つ目に
追加されるか曖昧になり、誤りに気付くのが遅れるため。

*出典: 仕様書.md §4.11*

## 10. 層構造とパッケージング

### 層を「直下 / core / toolbox / services」の4段にする

`toolbox` に部品を集めすぎて「外に触らない部品」と「外を触る道具」が混ざった状態に
なったため、4 段にした。

- **直下** — 何にも依存しない共通語彙（例外・定数・実行モード）。全層が使う
- **core** — 直下にだけ依存する部品。外にあるものは触らない
- **toolbox** — 外にあるもの（Excel・CSV・ブラウザ・Salesforce 等）を触る道具

層の定義と同層依存の例外一覧は `tests/test_layers.py` を正本とする。

**toolbox に集めすぎたから 4 段にした**: 「外に触らない部品」と「外を触る道具」が
混ざった状態になったため。

**社内固有かどうかでは分けない**: 社内 RPA 基盤のラッパーは社内にしか存在しないが
「呼び出すための部品」なので toolbox に入る。Salesforce の組織クラスも同じ。社内固有を
基準にすると sites が salesforce クライアントから切り離せず破綻する。

**土台を直下に残す**: Excel を使わないプロジェクトも `dry_run` / `constants` を
使う。`toolbox` に沈むと道具を使わない利用側まで toolbox を経由することになる。

*出典: 仕様書.md §4.30*

### utils を解体し、core は `_` を付けずに残す

層を 4 段に分けた後、利用者が `comken.core.*` を **47 行も直接 import している** ことが
分かった。`comken` 直下から何も公開していなかったため、`comken.core.logger` のような
長いパスを毎回打っていた。

- **`core/utils/`（曖昧な名前の箱）は解体。** `utils` には何が入るか説明できない名前で
  必ず物置になる。`clock.py` / `text.py` / `data.py` / `transfer.py` / `retry.py` /
  `wait.py` / `timer.py` は `core` 直下へ、`files/` は `core/files/` へ移した。
  **`helpers` / `common` / `misc` のような曖昧なフォルダを新設しない**
- **`Paths` は toolbox/windows/ へ移した。** レジストリを触る（`winreg`）ので
  「外にあるものを触らない `core`」の定義に合わない
- **toolbox は公開の階層に上げない。** 深いパスを残して**「外との接点」を import 行から読める**ようにする

#### `_core` へ改名して、戻した

一度 `comken/_core/` へ改名した（pandas が `pandas/core/` を持つが利用者は
`pd.DataFrame` 経由で取り、NumPy 2.0 が `numpy.core` を `numpy._core` へ改名した
「`_` を前置する」流儀に倣った）。**戻した**理由は 3 つ。

1. **アンダースコアが解決する問題を、公開の仕組み側が既に解決していた。** 目的は
   「利用者が `core` の深いパスを直接打つ」のを防ぐことだったが、`comken` と
   `comken.core` の 2 階層で届くなら、深いパスを打つ理由がそもそも無い
2. **`_` は守らせる仕組みを要求する。** 「`_core` を直接 import していないか」を
   検出するテストが無いと grep を手で打つ運用になって必ず腐る。**規約を減らす方が強い**
3. **矛盾が消える。** `python -m comken._core.config`（補完スタブの手動生成）は
   「利用者が触らない場所にあるコマンドを、利用者が打つ」という矛盾だった。
   `python -m comken core.config` なら矛盾しない

**公開／非公開はディレクトリ名ではなく `__all__` で表す。** 2 軸を分けておけば
公開方針を変えても import パスが壊れない。`_` をディレクトリ名に付けると 2 軸が
潰れ**「公開したくなったら移動」**になる（共有サーバーへ配置した後は互換性ポリシー
の対象になるので高くつく）。

*出典: 仕様書.md §4.31*

### 公開 API を「基本入口」と「部品」の2階層にする

優先順位は `from comken import X` を第一選択、そこに無いものは `from comken.core import Y` で取る。

**一度は直下に 30 個すべてを載せた経緯**: `_core` のままだと直下から出す以外に届ける
経路が無かったためで、`core`（`_` なし）に戻した時点でこの制約が消えた。
`from comken.core import DateFileFinder` が正規の経路になったので、直下を絞れる。

**絞るのは今しかできない理由**: 直下から名前を降ろすのは破壊的変更だが、
後から直下へ足すのは既存コードを壊さない。共有サーバーへ配置する前に絞っておき、
実運用で不便が出たら足す、という順序を取る。

**使用回数だけで決めなかった理由**: 実測では `Timer` / `retry` / `wait` / `zip_*` は
0 回。一方で `DateFileFinder`（5 回）は `Config`（4 回）より多いが、「ファイルを
扱わないプロジェクトも通る」ので `core` に置く。基準は使用回数ではなく
**「そのプロジェクトが何をするかに依存するか」**。

判定は `tests/test_facade.py`（直下と `core` の `__all__` の内容・重複が無いこと）と
`tests/test_layers.py`（層をまたぐ import の向き）を正本とする。

*出典: 仕様書.md §4.32*

## 11. リリースと後方互換

### v1.0.0 リリース宣言と SemVer 採用（2026-09-24）

**2026-09-24 に v1.0.0 をリリースした。** 祝日カレンダーの整理など、破壊的変更を
まとめて入れた最初の安定版で、**以降は SemVer ルールと互換性ポリシーに従う**。
バージョンの定義は `comken/__init__.py` の `__version__` の 1 か所だけ。

**0.X.Y は開発中扱い。** MAJOR が 0 の間は**機能追加でも MINOR を必ず上げる**。
API が安定していない前提なので、利用プロジェクト側は「マイナーが上がるたびに注意する」
運用になる。

**BO と intranet でバージョンを分けることはしない**（2026-09-24 決定）。どの版が動いて
いるかが分からなくなるのは版を固定しているために起きる問題で、版を分けても解決しない。
環境ごとの差は、同じタグを使ったうえで、各環境が使える機能・依存の範囲で扱う。

判断に迷ったら **MINOR を上げて**、仕様書の互換性ポリシーに従って旧名を残すと安全。

*出典: 仕様書.md §8 SemVer と v1.0.0*

### 例外クラスの統合（2026-09-25）

**対処が同じ例外だけを 1 クラスにまとめた**（138 → 120 クラス）。細かく分けた元の目的は、
非エンジニアが「何が悪いか」を分かるようにすることで、それは**メッセージ**が担っている。
一方 `docs/ERRORS.md` はエラー名（クラス名）から対処を引く表なので、
分類ごとに全部まとめると検索キーを失う。そのため、対処が違うものは残した。

- ファイルが無い 7 クラスは `ComkenFileNotFoundError` 1 つにした。標準の `FileNotFoundError` も継承する（`ConfigKeyNotFoundError` が `AttributeError` を継承するのと同じ形）
- 型で `except` されている例外や、利用側が個別に捕捉している例外は残した
- **comken 内で送出されない例外は「未使用」ではない。** 利用者プロジェクトが送出する想定のもの（`ExcelColumnNotFoundError`・`TransferSourceColumnNotFoundError`・`ScheduledDownloadFailedError`・`LoginFailedError` など）がある。
  また `ReportFolderNotFoundError` は、ダウンローダーが型で原因区分を決め、クラス名を履歴の「エラーコード」に書いていた。
  この4つは一度統合してから、利用側プロジェクトを grep して気づき、元に戻した
- 旧名は、いったん警告つきの別名で残したが、**同日に別名ごと削除した**（「旧名は全て消していい。警告もなしで」という判断）。
  v1.0.0 以降の互換性ポリシー（旧名は削除しない）の**例外扱い**。会社側プロジェクトで旧名を使っているコードは
  `ImportError` になるので、新しいクラス名へ書き換える
- 代償: `ComkenFileNotFoundError` は `ExcelError` などの配下ではないので、`except ExcelError` では
  「Excel ファイルが無い」を捕まえられなくなった

*出典: 2026-09-25 の例外整理（コミット `610d1b6` / `671bd95`）*

## 12. サイト／組織クラスの管理

### サイト／組織クラスには `OWNER` を必須にする

`SiteBase`（ブラウザ）と `SalesforceBase`（Salesforce 組織）は継承して使う前提だが、
**継承した事実がライブラリ管理者に届かないと、同じ社内システムのクラスが複数プロジェクトで
重複しても気づけない**。

ドキュメントの努力目標だけでは守れない（継承されたら読まれないことが多い）ので、
**起動時に `OWNER` の設定を強制する仕組み**にした。サブクラスは
`OWNER = "プロジェクト名 / 担当者"` の 1 行を書く。空だと `SiteOwnerRequiredError` で
起動が止まり、「`OWNER = "..."` を書く」という具体的な直し方を案内する。

検査のタイミングは**起動時**。`__init_subclass__` で import だけで落ちると影響が広い。
検証だけを `_check_start()` classmethod に集約する。

**検知ツールを作らない理由**: `OWNER` に適当な値を書けば起動できるので、そもそも
連絡なしの継承は止められない。止められないものを検知する道具を常設すると、
**その道具を保守する仕事だけが残る**。一覧が要るようになったらそのとき grep すればよい。

**管理者が扱うのは、連絡が来たものだけ**。**重複しても壊れるのは共有サーバーの
ライブラリではなく、連絡しなかった側**（片方の修正がもう片方に伝わらない）。
**`OWNER` を必須にしてあるのは、そのための痕跡を残すためで、監視のためではない。**

*出典: 仕様書.md §4.33*

## 13. Config のキャッシュ

### Config を解決済みパスごとにキャッシュする（2026-08-25）

`Config(path)` を `Path.resolve()` 後の絶対パスをキーに `functools.lru_cache(maxsize=128)`
でキャッシュし、プロセス内で 1 度だけ構築する。`from comken import config` 用の
デフォルト `Config()` も `_default_config_path()` で同じ関数を通るため、専用 global
変数は持たない（= 仕組みが 1 つ）。スタブ生成（`update_stub()`）も `_initialize` に
集約しているので同じパスならプロセス内で 1 回しか走らない。

**理由**: module-level `__getattr__` が `config.SECTION.KEY` を読むたびに `Config()` を
新規構築しており、そのたびに `config.ini` の読み直しと `.pyi` の書き出しが走っていた。
利用プロジェクトが 35,174 行のループの中で 1 行につき 4 回読んでおり、**14 万回の
ファイル I/O** になっていた。

**効果**: 1 回 12 ミリ秒 → 15 マイクロ秒。**利用者から見た使い方は変わっていない**。

**代償**: 同一プロセス内で `config.ini` を書き換えても反映されない。実務では
「`config.ini` を直す → ツールを動かす」は別プロセスなので問題ない。同一プロセスで
反映させたい場合は `_reset_cached_config()` を呼んでから再アクセスする（テスト用
内部 API）。

**`stat()` で更新確認する案を採らなかった理由**: 1 回 25 マイクロ秒（Windows 実測）
かかり 14 万回で 3.5 秒。共有サーバー上の `config.ini` ではネットワーク往復になり
更に遅くなる。業務ツールは実行中の設定変更を想定しないため毎回確認する利点が無い。

`functools.lru_cache(maxsize=128)` でキャッシュが増え続けないことを担保。
業務では 1〜2 種類のパスしか使わないので到達しない。

*出典: 仕様書.md §4.39*

## 14. 配置・運用

**3ファイルだけを配置時に書き換える**。このリポジトリは公開しているため、社内の名前・
URL・共有フォルダのパスは仮名で書いてある。配置時に書き換える 3 か所:

- `comken/toolbox/salesforce/sites/solution.py` — 本番組織の My Domain・認証情報の接頭辞
- `comken/toolbox/salesforce/sites/solution_sandbox.py` — サンドボックス組織の同
- `comken/services/salesforce_downloader/paths.py` — レポート管理表・履歴を置く共有フォルダ

**設定ファイルへ集約しなかった理由**: `settings.ini` と `settings.py` の両方を試して却下。
ini にすると設定がコードと ini に散り、Python ファイルに集めても書き換えるファイルは
減らない上に `Solution` の URL が `Solution` クラスから離れる。**クラスの値はそのクラスに
あるほうが、探さずに済む**。書き換え忘れは必ずエラーになる。

共有サーバーでは `git update-index --skip-worktree` で切り替えから守る。

**参照方式: 共有サーバーを直接参照**。comken は共有サーバー上の 1 か所に置き、
各プロジェクトはそこを**直接 import する**。

**直接参照方式の代償を受け入れた判断**: 「配布作業ゼロ・常に最新」が利点。
起動のたびにネットワークを読むので遅く、**共有サーバーが落ちると全プロジェクトが止まる**。
この代償を受け入れた上での方式。

**共有サーバーはタグだけを指す理由**（2026-08-15 決定）: **リリース済みのタグだけ**に保つ。
**共有サーバーでブランチをチェックアウトしない**こと（その瞬間に全プロジェクトへ伝播）。

**deploy.py のコピー方式を廃止した理由**（2026-08-14）: 共有サーバーで git が使えるので
廃止。コピー方式だと社内固有の値が毎回上書きされ毎回書き直すことになる。

**setup_comken.bat 廃止**（2026-09-08）: PC イメージ配布で `PYTHONPATH` が設定済みの
ため恒久登録スクリプトを廃止。共有フォルダ移動時はプロジェクト側の 3 か所
（`実行.bat` / `認証情報の登録.bat` / `.vscode/settings.json`）を手で書き換える。

**開発とリリース**。**開発は手元のクローン、共有サーバーはリリースしたタグだけを指す。**
共有サーバーを更新した瞬間に全プロジェクトへ伝播するため、「いつ切り替わるか」を
人が決められる形にする。

**master へ直コミットしてよい理由**: 1 人で開発しているので develop ブランチを分けても
「どちらが最新か」を管理する手間が増えるだけ。**共有サーバーがタグを指しているので、
master に何をコミットしても本番には流れない。**

**バージョンを上げる操作は配置に含めない理由**: 配置のたびに `__version__` を書き換えると
未コミットの変更を作ったまま配ることになり、「配った版がどのコミットか」が
`DEPLOYMENT.txt` を見ないと分からなくなる。

ロールバックは共有サーバーで前のタグに戻すだけ。
