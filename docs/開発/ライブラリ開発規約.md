# ライブラリ開発規約（comken 本体）

comken **本体（ライブラリそのもの）を編集する**ときの、ライブラリ固有のルールを定める。

> **言語レベルのコーディング規約（命名・型ヒント・定数・例外の書き方・ロギング・
> モジュール内の並び順など）は [CONVENTIONS.md](CONVENTIONS.md) に従う。**
> 本書は「多くのプロジェクトから共有されるライブラリ」という立場ゆえに追加で守るルールだけを扱う。
> comken を"使う側"のプロジェクトは `templates/新規プロジェクト/` の雛形から作る。

ログの設定（出力先・フォーマット・レベル）は社内の共通ライブラリ側で行う。
comken 本体では `logging.getLogger(__name__)` を使うだけでよい。

`from __future__ import annotations` は一律に追加しない。必要条件と理由コメントは
[CONVENTIONS.md「型ヒント」](CONVENTIONS.md#型ヒント) に従う。

## 公開 API の管理

### `__all__` で公開範囲を明示する

```python
# comken/toolbox/excel/__init__.py
from comken.toolbox.excel.reader import ExcelReader
from comken.toolbox.excel.sheet import Sheet
from comken.toolbox.excel.writer import ExcelWriter

__all__ = ["ExcelReader", "ExcelWriter", "Sheet"]
```

`__all__` を書くと内部の実装クラスが外に漏れ出さない。**新しく公開したいものだけ**を `__all__` に足す。

- 基底クラス（`FileBase` / `CsvBase` / `ExcelBase`）は本体の実装構造なので
  `__all__` に載せない。利用側は具象クラスだけを使う。
- **利用者に変換や前処理をさせるくらいなら、公開メソッド側で受け入れる。**
  例えば Excel の列は `"A"` / `"AA"` / 数値のどれでも指定できるようにする。
  列記号の変換関数を公開せずに済むため、**「補助関数を公開する」より
  「本体が気を利かせる」方を選ぶ。**

### 内部ヘルパーには `_` プレフィックスを付ける

```python
class ExcelWriter:
    def read_rows(self, sheet_name: str) -> list[tuple]:  # 公開メソッド
        ws = self._sheet(sheet_name)
        ...

    def _sheet(self, sheet_name: str):  # 外から直接呼ばないという意味
        ...
```

`_` 付きは「利用側が呼ぶことを想定しない」という宣言。将来シグネチャを変えても互換性を気にしなくてよい。

### 公開は「基本入口」と「部品」の2階層にする

**`comken` 直下（`from comken import ...`）に置くのは、何をするプロジェクトかに
関係なく使う土台だけ。** 設定・ログ・実行モードの3種類しか入っていない。

**部品は `comken.core`（`from comken.core import ...`）から公開する。**
特定の操作対象（ファイル・日時・文字列・差分・計測）を持つものはこちら。

**公開名の一覧はここに書かない。** 正本は `tests/test_facade.py`（機械可読）で、
使う側向けの一覧は README「使うときの約束」にある。
足すときは `tests/test_facade.py` の期待値を直すことになるので、そこが
「本当に全プロジェクトで使うか」を通す関門になっている。

**機能を提供するクラスは `comken.toolbox.excel` のように機能パッケージから公開する。**
toolbox / services は上の2階層に上げない。
`from comken.toolbox.excel import ExcelWriter` のように深いパスのままで十分で、
そこには「どの機能群に依存しているか」が読める意味があるため。

書くときの順序は **`from comken import X` が第一選択、そこに無いものだけ
`from comken.core import Y`**（仕様書 §4.32）。同じ名前を両方から取れる状態にしない
（`tests/test_facade.py` が重複を検出する）。

内部実装（基底クラス・転記の内部ヘルパー・一時ファイルの掃除・列番号の変換など）は
どの階層の `__all__` にも載せない。載せない名前の一覧は `tests/test_facade.py` が正本。
**公開／非公開はディレクトリ名ではなく `__all__` で表す** ——
ディレクトリは「何であるか」で決め、公開範囲は `__init__.py` で決めることで、
公開方針を変えてもファイルが動かない（＝ import パスが壊れない）。

## サイト／組織クラスを昇格させる基準

`SiteBase`（ブラウザ）と `SalesforceBase`（組織）は継承して使う前提のクラス。
ライブラリ管理者は「誰かが継承してサイト／組織クラスを作った」という事実を
**ドキュメントの努力目標ではなく起動時の検査**で把握する。サブクラスには
`OWNER = "プロジェクト名 / 担当者"` を必ず書いてもらい、
`comken.toolbox.browser.sites` / `comken.toolbox.salesforce.sites` 配下の
クラス（管理者が昇格を判断したもの）は検査を免除する代わりに `OWNER = "comken"` を書く。

### まず `sites/` か `services/` かを決める

社内システムを足すとき、置き場所は**2つある**。どちらか片方とは限らず、両方になることもある。

| 足すもの | 置き場所 | 見分け方 |
|---|---|---|
| **そのシステムへの入り方**（URL・ログイン・行ける画面） | `toolbox/browser/sites/`<br>`toolbox/salesforce/sites/` | **「〜を操作する」で説明できる** |
| **そのシステムを使った社内の手順**（管理表の決まり・保存先の規約・管理番号） | `services/` | **社内の決まりを知らないと説明できない** |

勤怠システムを例にすると:

- 「勤怠サイトを開いて打刻画面へ行く」→ **`sites/`**。サイトの形が分かれば誰でも書ける
- 「毎月末に管理表の全員分を締めて、決まった場所へ決まった名前で出す」→ **`services/`**。
  社内の決まりを知らないと書けない

**サイトクラスは `services/` に置かない。** 画面の操作そのものは社内の決まりではなく、
「そのサイトがどうできているか」だから。逆に、管理表や保存先の規約が絡んだ時点で
`services/` の話になる（`salesforce_downloader` がその形）。

**どちらも、まずはプロジェクト側に置く。** 下の原則は両方に当てはまる。

### 原則: 最初は必ずプロジェクト側に置く

新しい社内システムの自動化を作るときは、**必ずプロジェクト側（`src/sites/` や
そのプロジェクト独自の置き場所）に置く**。最初からライブラリへ入れる判断はしない。

後からライブラリへ昇格するのは非破壊的だが、最初にライブラリに入れてしまうと
「外で使うには comken 経由でしか書き始められない」状態になり、外せなくなる。

### ライブラリへ昇格する判断基準

次のいずれかに当てはまったら、ライブラリへ移すことを検討する。

- **2つ目のプロジェクトが同じシステムを触り始めた時点**（重複が実測で出たとき）
- **全社共通の業務システムで、複数プロジェクトから触るのが確実なとき**
- **認証情報（DPAPI のキー名）を伴い、登録名を統一したいとき**
  （例: `kintai_client_id` を複数プロジェクトで同じキーで登録したい）

逆に、**1つのプロジェクトしか触らないうちはプロジェクト側に置く**。
次のようなケースもプロジェクト側に置いてよい。

- 画面が頻繁に変わる、または試験的な自動化のとき
- そのプロジェクト固有の手順（社内申請のフォーマット等）を含むとき

### 昇格の手順

1. プロジェクト側の `src/sites/<システム>.py` を、ライブラリ側の
   `comken/toolbox/browser/sites/<システム>.py`（Salesforce の場合は
   `comken/toolbox/salesforce/sites/<システム>.py`）へ移す
2. クラス内の `OWNER` を `"comken"` に変える（管理者が昇格した印）
3. ライブラリ側の `__init__.py` の `SITES` タプルにクラスを追加する
4. 利用側の import を `from comken.toolbox.browser.sites import <クラス名>` へ書き換える

**移すかどうかはライブラリ管理者が判断する。** プロジェクト側は勝手に
`comken` 配下へファイルを置かず、必ず管理者へ連絡する。

### 衝突防止

ライブラリへ昇格したあと、プロジェクト側で同じ `NAME` のクラスを定義すると、
**起動時に `SiteAlreadyInLibraryError`** で止まる。「すでにライブラリにあるものを
自作している」状態を自動で捕まえるのが目的。

### 管理者が扱うのは、連絡が来たものだけ

**無断で継承されたクラスを探しにいく仕組みは作らない。** `OWNER` を必須にしても、
適当な値を書けば起動できるので、連絡なしの継承は止められない。**止められないものを
検知する道具（走査ツール・利用履歴・事前登録）を常設すると、その道具を保守する仕事だけが残る**
——走らせなければ腐り、書き込み先の権限を管理し続けることになる。

ライブラリ管理者が扱うのは**連絡が来たものだけ**とする。連絡なしに作られたサイト／組織
クラスは、そのプロジェクトの持ち物として扱う。**重複しても壊れるのは共有サーバーの
ライブラリではなく、連絡しなかった側のプロジェクト**（同じシステムのクラスが2つあると、
片方の修正がもう片方に伝わらない）。

一覧が要るようになったら、そのとき `OWNER` を grep すればよい。**`OWNER` を必須に
してあるのは、そのための痕跡を残すためで、監視のためではない。** 起動時に止めるのは、
継承する人に「これは誰の持ち物か」「ライブラリに入れるべきか」を一度考えてもらう関所として。

## カスタム例外の階層設計

すべての例外は `ComkenError` を基底とする1本の階層にする。
利用側が `except ComkenError` でライブラリ由来のエラーをまとめて捕捉できるようにするため。

**階層の全体像は [仕様書「例外体系」](仕様書.md#5-例外体系) が正本**（ここに図を再掲しない。
例外を足すたびに2箇所を直すことになり、片方が必ず古くなる）。

カスタム例外の書き方そのもの（1つの失敗＝1クラス、メッセージは `__init__` で組み立てる、
素の `Exception` を投げない等）は [CONVENTIONS.md「例外」](CONVENTIONS.md#例外) に従う。
本体へ例外を足すときは、それに加えて次を守る。

| ルール | 理由 |
|---|---|
| 必ず `ComkenError`（または既存の中間クラス）を継承する | 利用側の `except ComkenError` から漏れないようにする |
| **`comken/exceptions/__init__.py` の import と `__all__` に必ず追加する** | 載せ忘れると `from comken.exceptions import ...` で取れず、**`ERRORS.md` の生成対象にすら入らないので気づけない**（下記） |
| docstring に「対処:」を書く | `ERRORS.md` はここから生成される。書き忘れると生成が止まるので、空欄のまま配られることはない |

> **`__all__` への追加漏れは自動検出されない。** 対処法の書き忘れは生成が止まって気づけるが、
> `__init__.py` に載っていない例外はそもそも生成の入力に入らないため、静かに漏れる
> （2026-08-14 に `SalesforceCredentialRotationError` で実際に起きた）。
> 例外を足したら `from comken.exceptions import 新しい例外名` が通るか確認すること。

```python
class ExcelFileNotFoundError(ExcelError):
    def __init__(self, path: object) -> None:
        super().__init__(
            f"Excel ファイルが見つかりません: {path}\n"
            "パスが正しいか、ファイルが存在するかを確認してください。"
        )

# 送出側
raise ExcelFileNotFoundError(src)
```

- 例外は握りつぶさない（`except: pass` は禁止）。
- 行単位の処理エラーは行番号を含めて再送出する（`transfer_by_letter` 等）。

## 破壊的変更と互換シム

comken は共有フォルダ配布で**全プロジェクトが常に最新を参照する**。
名前を黙って変えると、更新した瞬間に各プロジェクトが動かなくなる。だから旧名は消さずに残す。

| ルール | 内容 |
|---|---|
| 旧名には警告を付けて残す | `comken/deprecation.py` の `warn_renamed(旧名, 新名)` を使う |
| 警告は `FutureWarning` を使う | `DeprecationWarning` はデフォルト非表示で気づけない |
| 旧 import パスはシムにする | 下記のように `__getattr__` で新モジュールへ誘導する |

```python
# comken/old_name.py（旧名の互換シムの例）
from comken.deprecation import warn_renamed
from comken.new_name import NewClass as _NewClass

def __getattr__(name):
    if name == "OldClass":
        warn_renamed("comken.old_name.OldClass", "comken.new_name.NewClass")
        return _NewClass
    raise AttributeError(name)
```

- 「利用者ゼロ」が確実な場合（リリース前・社内展開前）はシムを作らず単純に改名してよい。
- パッケージ名は `comken` で確定している。名前の変更は互換性の対象外とする。

## パッケージ構成

- **ライブラリのコードは `src/` レイアウトにしない。** リポジトリ直下に `comken/` を置く。
  各 PC が共有サーバーのリポジトリルートを `PYTHONPATH` で直接参照するため、`comken/` が
  直下にある構成を前提にしている（pyproject も同様）。src レイアウトへの
  移行は「テスト隔離」という小さな利点に対し、参照フローを壊すリスクが大きく、YAGNI。
- 層は **直下 / core / toolbox / services** の4段にする。詳しい基準は `仕様書.md §4.30` を参照。
  層の定義と同層依存の例外一覧は `tests/test_layers.py` を正本とする。
- 小規模な公開定数は `comken/constants.py` にまとめ、何にも依存しない最下層とする。役割や量が
  明確に増えた場合だけパッケージ分割を検討する。
- **`core` には曖昧な名前のフォルダ（`utils` / `common` / `helpers` / `misc`）を作らない。**
  物置になるので、`files` / `naming` のように目的が具体的になった単位で切る。
  「何が入っているか外から説明できない」時点で、利用者へ公開する単位にはできない。
- `core/files/` はファイル探索・操作・圧縮・命名方式を集約する。命名方式は `core/files/name.py` に
  クラスを追記する形で増やす。1〜2 個しかないうちはパッケージ化しない。
  パス取得（`Paths`）はレジストリを触るため toolbox/windows/ へ置いた（`core` の定義に反するため）。
- 機能パッケージ同士は原則独立にする。依存は**下から上には向けるが、上から下には向けない**。
  toolbox パッケージは core・直下・同層に依存してよい。services はすべてに依存してよい。
  例外的な依存（`excel` → `windows` の COM フォールバック等）は遅延 import にして、
  片方が入っていない環境でも単体で動くようにする。
- 外部ライブラリ依存を使うフォルダは、
  import 時に対処法つきのエラーを出し、そのフォルダを使わなければ影響しないようにする。

> ライブラリ本体の「src レイアウトにしない」は、雛形プロジェクトが `main.py` を
> ルートに置くのとは別のトピックなので混同しないこと。

## 品質確認

変更時はRuff、フォーマット、pytest、Markdownリンク検査を実行する。実行件数や監査日を
文書へ転記するとすぐ古くなるため、結果はCIとGit履歴を正本にする。

次の境界はモックだけでは保証できない。関連機能を変更したリリースでは実機で確認する。

- Excel / Access / OutlookのCOM差異、Officeの版差、権限、ファイルロック
- SeleniumとEdgeDriverの版差、ポップアップ、証明書、ダウンロード完了判定
- Salesforce組織ごとの権限、ECAのレスポンス項目、API制限
- DPAPIのWindowsユーザー・PC間の非互換性
